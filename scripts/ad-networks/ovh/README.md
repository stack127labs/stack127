## Domain Rating

The proposed cron entry is `5 7-23 * * * .../run-job.sh domain-rating --limit 500 --time-budget-minutes 30` (UTC). It leaves 00:00–06:59 for the existing daily jobs and 05:00–06:59 release window. Collection ends by :35. A slow or contended sync can overrun into :40 and make hourly verification skip once. This occasional skip is acceptable: the next hourly run resumes due checks, and missed enrichment runs select due work again. Repeated skips need investigation; the existing lock/retry wrapper remains authoritative. Preserve current pauses and unrelated jobs when the lead adds this line to the installed crontab after review.

The job needs **`AHREFS_API_KEY` in Infisical project `stack127`, folder `/vps/ad-networks`, environment `prod`** (`stack127 /vps/ad-networks`). This is the same API key used by launch directory metrics, copied through Infisical, not a new public/build variable. Cockpit `workflow/infisical.md` maps that folder to `/srv/stack127-data/ad-networks.env`. Homelab's existing sync writes that file. There is no ad-network `prepare-env` script. The lead adds the named key through `infisical-env`; never edit the OVH file or read-only Mac mirrors. Do not put it in Dokploy, GitHub, or `NEXT_PUBLIC_*` variables. The launch directory folder stays unchanged.

The collector uses the [free Ahrefs endpoint](https://docs.ahrefs.com/en/api/reference/public/get-domain-rating-free), `dr3`. It makes one request at a time, at least three seconds after the previous response. `--pace-ms` can slow it down (3000–60000), never speed it up. All retries share that clock. HTTP 429 honors numeric or dated `Retry-After`, with 30/60 second exponential backoff. A third 429, a delay longer than 60 seconds, or HTTP 401/403 stops the run and reports failure. It does not try other domains after the stop. Both this job and the monthly launch-directory metrics job use `/srv/stack127-data/state/ahrefs.sqlite`. A separate process-held SQLite lock in `ahrefs.sqlite.lock` serializes requests across both jobs and releases automatically on process death. Before HTTP starts, the state file commits a reservation for now plus the configured pace. HTTP completion extends that reservation. A 429 commits its Retry-After cooldown before body cleanup or callbacks. These committed values survive a hard kill, including cooldowns longer than an hour. A crash before the cooldown commit can retain only the pre-request pacing reservation. Authentication failures stop the current requester; they are not saved as shared stop states. The job user needs write access to that directory. The ad-network SQLite checkpoint also retains its own retry time. A run before that time reports the retained rate limit without HTTP requests. No attempt bypasses the limit.

Priority: never-checked sites with a confirmed/stale manager relationship, other confirmed/stale sites, other never-checked sites, then the oldest successful dates strictly older than 30 days. Pending candidates stay local until the existing sync admits their reviewed relationships. Failed lookups retain both the prior value and successful date; a separate 24-hour retry checkpoint prevents bad domains from starving the queue. Successful zero is a measurement. Successful values are rounded to integers, 0–100; unknown stays null.

Seventeen daily runs can measure at most 8,500 domains a day. OVH has 213,003 candidates: 123,361 listed and 39,823 managed. Managed sites take about 5 days; full first coverage takes about 26 days without throttling or slow responses. These groups overlap, so do not add them together. Steady state picks up dates after 30 days, so a full refresh cycle takes roughly 30 days plus the queue delay. Recheck capacity if the source exceeds 255,000 domains or upstream throttling persists.

Each successful measurement and its checkpoint commit in one SQLite transaction. SIGTERM/SIGINT and the time budget cancel sleeps/HTTP; completed measurements remain. A restart retries unfinished work without losing or duplicating measurements. The existing wrapper uses a process-held `flock`, `nice`, time-bounded children, sync-lock retries, and the standard `== <UTC> start domain-rating ...` / `== <UTC> end domain-rating exit <code>` log lines. Missed runs catch up by selecting due work at the next hour. The existing log rotation and automation manifest cover `logs/domain-rating.log`. Failure exits nonzero and the existing alert path handles it.

After collection (including a failed partial run), `refresh.mjs` syncs all changed reviewed rows through the existing 500-row PostgreSQL batches, then calls the existing origin revalidation step once. There is no per-domain sync. SQLite candidates without a reviewed relationship are not sent to PostgreSQL. Sync hash checkpoints make retries harmless. The new migration excludes only DR and its checked date from the frontend source projection, so DR-only updates produce no cache event/source revision and no Cloudflare rebuild. Other enrichment or relationship changes in the same sync still queue their normal refresh. DR values are public on pages and APIs with linked Ahrefs credit. The daily snapshot at 00:10 UTC always inserts a dated row and queues a refresh, publishing new DR values daily even when the counts stay unchanged. Other public record changes can publish DR sooner.
