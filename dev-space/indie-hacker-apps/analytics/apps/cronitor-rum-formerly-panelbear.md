## Cost examples — our calculation

Checked 2026-11-05. Inputs: [current tariff](https://cronitor.io/pricing), [billable event definition](https://cronitor.io/docs/rum-faq), [automatic collector switches](https://raw.githubusercontent.com/cronitorio/cronitor-rum-js/master/src/config.ts) and [general payment terms](https://cronitor.io/terms). Keep the published dollar symbol ($); no currency conversion or tax assumption is made.

Website comparison assumptions: one Site, one dashboard user, 100% collection, no uptime/job/heartbeat monitors, no site alert add-on, no SAML/status-page/browser-check add-ons, no custom events. Turn off automatic error and Web Vital capture to model **one accepted Pageview event per pageview**. Ordinary page-load timing fields are included in that pageview payload in the [collector source](https://raw.githubusercontent.com/cronitorio/cronitor-rum-js/master/src/collectors.ts). The unmodified default can emit extra events, so its actual bill cannot be derived from pageviews alone.

| Monthly workload | Plan/model | Inputs and formula — our calculation | Result and limits |
| --- | --- | --- | --- |
| 10,000 pageviews, pageviews only | Hacker | 10,000 accepted events <= 100,000 free events; one included user; free subscription $0 | $0 subscription while within the allowance. This is not an estimate for default automatic Web Vital/error capture. |
| 100,000 pageviews, pageviews only | Hacker | 100,000 accepted events <= the published 100,000-event allowance; one included user | $0 subscription at the stated allowance. Exact boundary enforcement/grace is not documented; extra automatic or custom events would exceed the modeled workload. |
| 1,000,000 pageviews, pageviews only | Business tariff model | (1,000,000 / 100,000) x $10 + 1 user x $5 + 0 monitors x $2 = $100 + $5 | **$105/month modeled tariff components. Exact invoice cannot be established:** the pages do not explain a paid-plan free-event offset, tax or event reconciliation. No Hacker allowance is silently subtracted. |
| 100,000 pageviews + 100,000 custom events; no other events | Business tariff model | 200,000 accepted events; (200,000 / 100,000) x $10 + 1 x $5 = $20 + $5 | **$25/month modeled tariff components**, with the same invoice uncertainties. Custom events share the event meter. |

| 10,000,000 accepted events; one user; no monitors/add-ons | Business event-only scenario | (10,000,000 / 100,000) x $10 + 1 x $5 = $1,000 + $5 | **$1,005/month at the public list rate**, before unpublished volume discounts, tax and any account-specific allowance. The paid examples use exact whole 100,000-event multiples so they do not invent partial-block rounding. A smaller paid workload cannot be priced exactly from “$10/month per 100,000 events” without knowing whether billing is proportional or block-based. Sampling, filters, duplicated manual events, errors and Web Vital occurrences change accepted event volume; no fixed multiplier is guessed. Native-mobile, replay and MRR cost scenarios do not apply to the documented browser RUM product.

## Conflicts and unknowns

- **Localhost default conflict:** [product page](https://cronitor.io/real-user-monitoring) says localhost is dropped by default. [Sites API](https://cronitor.io/docs/sites-api) and [client configuration](https://raw.githubusercontent.com/cronitorio/cronitor-rum-js/master/src/config.ts) say false; API examples sometimes show true. Different creation paths could explain it, but that was not tested. Record the conflict and require explicit configuration.
- **Billing details:** [pricing](https://cronitor.io/pricing) says actual monthly usage; [terms](https://cronitor.io/terms) say recurring subscriptions are charged in advance. The exact metered-event settlement process is unclear. Pricing, FAQ and terms do not settle partial-block rounding, paid-plan treatment of the Hacker allowance, tax inclusion, a spend cap, free-quota enforcement or quota alerts. Guessed /docs/billing and /docs/rum-pricing returned 404; neither is used as affirmative evidence.
- **Retention:** [pricing](https://cronitor.io/pricing) states 12 months for Business; [FAQ](https://cronitor.io/docs/rum-faq) gives six months only as an example of a plan's retention. These are not conclusively contradictory because the example is not assigned to a named plan. Hacker/Enterprise RUM retention, raw versus aggregate/error clocks, trial expiry, post-cancellation collection and restore/backfill behavior remain unestablished. [Sites query maximum range](https://cronitor.io/docs/sites-api) of 730 days is not a retention promise.
- **Privacy scope:** [general privacy policy](https://cronitor.io/privacy) describes account/website cookies, IP logs, customer processing and subprocessors. [RUM-specific page](https://cronitor.io/real-user-monitoring) says its tracker has no cookies or stored visitor IPs. These are different scopes, not grounds to claim the whole Cronitor website is cookieless. [Collector code](https://raw.githubusercontent.com/cronitorio/cronitor-rum-js/master/src/collectors.ts) sends raw browser metadata and path-bearing referrers; the displayed hostname reports are narrower. The backend session hash/ID construction and rotation are not explained in the FAQ, multi-domain docs or public client source.
- **Contracts and location:** [security](https://cronitor.io/docs/security) names US/EU AWS infrastructure, but does not establish selectable EU-only RUM processing or backup locations. Privacy, security, terms and the docs index did not expose a public DPA. Direct /dpa and /data-processing-agreement returned 404; /docs/rum-data-privacy and /docs/rum-data-policy also returned 404. These failed guesses do not prove no DPA can be supplied privately. No provider was contacted.
- **Consent and account age:** [quickstart](https://cronitor.io/docs/rum-quickstart) asks operators to review consent requirements; [privacy](https://cronitor.io/privacy) puts customer-site compliance on the customer. No jurisdiction-specific universal exemption is established. Privacy permits a guardian representation for minors, while [terms](https://cronitor.io/terms) require users to be 18; use the stricter explicit account eligibility and do not claim a minor can register.
- **Portability and legacy:** RUM overview, FAQ, quickstart, Sites API and rename page did not establish CSV/PDF or full raw-event export, historical GA/CSV import, or current Panelbear account/history migration guarantees. The old brand's redirect confirms naming continuity, not identical data access or old pricing. A guessed /src/session.ts file returned 404; no backend identifier algorithm was inferred.
- **Other feature gaps:** Custom-event docs and Sites query fields do not establish persistent-user identify/merge, cohort retention, funnels, native mobile, replay or recurring-revenue accounting. Dedicated WordPress/site-builder support and a complete UI-language list were not established from the docs index and setup pages. Public report flags do not establish a working account-free RUM demo.
- The correct first-person acquisition announcement was readable through search. An earlier guessed announcement slug returned 403; it was not used as proof. The current Panelbear redirect returned HTTP 308 to a direct Python reader, but its Location and the destination were inspected, and the web reader followed it successfully.
