## Conflicts and unknowns

- **Lifecycle and ownership:** Checked the official repository/default README, GitHub release metadata, publisher package, docs/security/contribution information and official-domain shutdown/sunset/acquisition searches first. No whole-project ending/acquisition notice was found in this bounded check. The repository is not archived or disabled. A third-party discussion claiming abandonment was not used as proof. The maintainer's published note says allauth support is optional/narrow and that most expansion requests will be declined; this is scope guidance, not a project shutdown.
- **Published package versus development docs:** PyPI/GitHub latest release is 7.2.0 from March 15, 2026. Current live docs and later default-branch code include passkeys from an April 25 commit. The 7.2.0 tag/setup/PyPI metadata do not define with-passkeys or passkey source implementation. The publisher's source archive was inspected directly, in memory: it has no passkey .py files and includes 45 cached passkey-related .pyc files. Those cache files were not loaded, decoded as executable code, installed or run. Their presence does not establish a supported released feature, dependency recipe or migration contract. F22 preserves the live-doc/artifact discrepancy; development facts are not counted as normal 7.2.0 availability.
- **Recovery-code method conflict:** The released MFA guide lists GET mfa/recovery-codes/. The released RecoveryCodesView implements post() and no get(). The file records the conflicting sources and uses source behavior to identify the implemented method. No endpoint was called to test it.
- **DRF minimum conflict:** Setup/PyPI metadata allow DRF >=3.13.0, while the same release's index/upgrade documentation says >=3.14. Both are retained. An install constraint is not a proven compatibility matrix for every future dependency version. Current allauth also has its own Python requirements, which can narrow the base package's Python range.
- **Stale release-history label:** The bundled changelog calls 7.1.0 the latest stable version even though official GitHub/PyPI show 7.2.0. Its early naming-transition headings are also inconsistent, so no exact historical rename version/date is asserted. Current package identity is clear; the old django-rest-auth imports/package should not be silently treated as this current module.
- **MFA integration scope:** Read the full 7.2.0 MFA guide, routes/views/serializers, TOTP/recovery implementation and settings. Setup explicitly requires routing password login through MFALoginView. Installing the module does not replace every ordinary/social/admin/custom login route or mandate enrollment. TOTP and recovery data are not allauth.mfa data. TOTP secret signing is not encryption; recovery codes derive from stored seed/state. No new vulnerability exploit or security test was performed.
- **Tokens, sessions and defaults:** Read core login/logout/change code, JWT cookie code, DRF Token schema, Django sessions/auth-hash behavior and SimpleJWT 5.5.1 defaults/blacklist docs. DRF token, Django session, JWT access and JWT refresh have different lifetime/revocation behavior. Deleting a cookie or changing a password is not proof that every issued token/device is revoked. JWT rotation, blacklist and cookie/CSRF examples must not be reported as library defaults.
- **Social/SSO boundaries:** Read the project's social guide/serializers/views, maintainer scope note and each named allauth provider's official page. Google/GitHub/Facebook have project recipes; Apple has explicit serializer handling; Microsoft has an upstream adapter/custom integration path without a wrapper-specific platform matrix. SAML's upstream browser/ACS flow is not the SocialLoginSerializer OAuth token contract. OIDC token parsing/issuing, SAML, customer organizations and SCIM are separate capabilities; no full allauth feature set was inherited.
- **Unlinking safety:** The released wrapper calls the allauth adapter's validate_disconnect hook. In the inspected current allauth source, that hook itself is empty. Safeguards from allauth's different internal disconnect flow cannot be carried over. App-specific last-credential/reauthentication policy needs deliberate implementation and review.
- **Organizations/SCIM:** Checked all released account/registration/MFA routes, endpoint docs, full file inventory and profile/role examples. No bundled SCIM provisioning implementation was found. Customer organization invitations/isolation are not provided by a Django Group example; allauth explicitly puts invitations outside its scope. Both fixed business scenarios are unsupported by dj-rest-auth alone.
- **Migration and retention:** Read serializers/user-data/schema ownership, Django serialization/password/deletion/session docs, token/MFA models, upgrade guidance and SimpleJWT cleanup docs. Exports can preserve data the operator stores, but foreign password hashes, provider IDs, signed MFA data, custom profile/phone tables and token settings need compatible handling. Account deletion does not promise erasure of backups/logs/external identities. No universal migration wizard, token portability or deletion deadline was invented.

Project docs/source/examples do not establish a complete native SDK/OS passkey matrix or allauth-independent customer UI.
