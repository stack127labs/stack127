## Cost examples: our calculation

The consumer baseline is one production app and one builder/admin, with 1,000 / 10,000 / 50,000 / 100,000 distinct previously registered password users returning on two or more days. No customer organizations, business SSO, SMS or paid security is included. We select existing verified password users without an enrolled email/SMS factor and without forced MFA. The default optional MFA offer can be skipped; ordinary password returns require no per-login message.

Software has no upstream monetary license fee. Zero is displayed as $0 for comparison; this is not a dollar-denominated managed plan, a currency conversion or a promise of zero infrastructure cost. There is no Authorizer MAU billing formula. The full running total is software + compute + database + any shared Redis + storage/backups/network + external delivery/support actually used + operating work. User counts do not settle these costs, and no hosting or developer-time estimate is made.

Business A is 1,000 users in 10 active customer organizations × 100 members with one active SAML connection. Business B is 10,000 users in 100 organizations × 100 members with 10 active SAML connections. Both require membership, invitations and roles; neither requires SCIM. Native memberships/roles/SSO are confirmed. The verified platform invitation API does not attach an organization, invite an existing user to it or expose an org-admin acceptance workflow. A complete native org-specific invitation baseline is therefore not established; additional application logic is required. Conditional zero license arithmetic below is not a complete turnkey B2B plan quote.

All six states describe the complete cost/fit answer. `unclear` retains unpriced operating totals and, for business cases, the invitation-workflow gap. No trial credit, annual discount, negotiated contract, third-party host rate or optional paid feature is substituted.

## Conflicts and unknowns

- **Version sunset and lifecycle.** The [security policy](https://raw.githubusercontent.com/authorizerdev/authorizer/main/SECURITY.md) labels 1.x EOL and current 2.x supported. No separately dated 1.x sunset announcement was found. Read [official site](https://www.authorizer.dev/), [official blog](https://blog.authorizer.dev/), [repository](https://github.com/authorizerdev/authorizer), [2.4.4 release](https://api.github.com/repos/authorizerdev/authorizer/releases/latest) and [governance](https://raw.githubusercontent.com/authorizerdev/authorizer/main/GOVERNANCE.md) for product shutdown/acquisition notices; none were found. A draft foundation-transfer possibility is not an acquisition. Current maintenance evidence is 2.4.4, November 1, 2026, plus an unarchived repository.
- **Self-hosted software and legal scope.** [official site](https://www.authorizer.dev/) and [released Apache license](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/LICENSE) describe free software operated on your infrastructure. No paid/hosted rate card or product subscription trial was established. Guessed official paths https://www.authorizer.dev/pricing, https://www.authorizer.dev/terms, https://www.authorizer.dev/privacy and https://www.authorizer.dev/privacy-policy returned 404. Site/docs/governance/license and official legal/privacy searches yielded no dedicated product privacy policy, DPA/subprocessor schedule or paid support terms. The [official blog](https://blog.authorizer.dev/) links Hashnode’s platform terms/privacy; those do not establish an Authorizer end-user-data agreement. License/NOTICE are actual published software terms, and your cloud/sender contracts remain separate.
- **Cost limits.** Apache’s zero upstream monetary fee is not an all-in operating total. Read [configuration reference](https://docs.authorizer.dev/core/server-config), [database guide](https://docs.authorizer.dev/core/databases), [Docker guide](https://docs.authorizer.dev/deployment/docker), [rate-limit guide](https://docs.authorizer.dev/core/rate-limiting) and [email guide](https://docs.authorizer.dev/core/email). Compute, database, optional shared Redis, backups/network, sender volume and operating time are not settled by the fixed user counts. All six calculations keep those costs unknown; no generic cloud price or staff-hours estimate is invented. Existing verified password returns need no compulsory email, while verification/magic-link/recovery/email-MFA choices can send messages.
- **Customer organizations versus platform invitations.** [organization guide](https://docs.authorizer.dev/enterprise/organizations) confirms native multi-org membership, independent per-org roles and namespaced org-admin delegation. [domain-routing guide](https://docs.authorizer.dev/enterprise/org-domains) says domain verification only routes login. [invitation API section](https://docs.authorizer.dev/core/graphql-api#_invite_members), [released invitation service](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/internal/service/admin_access.go) and [released API schema](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/internal/graph/schema.graphqls) show platform-only invitations: at most 100 emails/request, new addresses only, no org_id, no membership assignment, super-admin only, 30-minute verification record. Business requirements therefore need additional app-managed customer invitation/acceptance logic. Native membership/roles/SSO are not priced as a complete standalone organization-invitation product. No universal total org/member cap was found in those guides/config/schema; one incoming OIDC and one SAML connection per org are explicit.
- **SCIM behavior is specific.** [SCIM guide](https://docs.authorizer.dev/enterprise/scim) scopes access by per-org bearer token, treats user DELETE as deactivation, revokes access on active=false, and supports a limited filter/list surface. Unsupported user PATCH attributes can be skipped while unsupported group paths error; this is not full generic directory parity. Groups are represented with org-scoped FGA membership tuples. No live provider integration test was performed. This feature is in the open-source server, despite its Enterprise documentation category.
- **Current security docs supersede legacy API prose.** [configuration reference](https://docs.authorizer.dev/core/server-config), [security-hardening guide](https://docs.authorizer.dev/core/security) and [released API schema](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/internal/graph/schema.graphqls) describe optional/skippable first enrollment, multiple enrolled methods, token withholding and explicit MFA flags. The [GraphQL guide](https://docs.authorizer.dev/core/graphql-api) login paragraph still says only one MFA at a time, and several examples mention removed env toggles/admin cookie wording. Its delete-user section says id is required but retains an email-keyed example; [released user admin service](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/internal/service/admin_users.go) takes id. Do not reuse stale examples as current request shapes. Email/password changes, passkey verification gates, social email attestation and org identity correlation also have different rules.
- **Identity and missing account methods.** Read [email-attestation contract](https://docs.authorizer.dev/core/email-verification-contract), [OIDC broker guide](https://docs.authorizer.dev/enterprise/org-sso-oidc), [released API schema](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/internal/graph/schema.graphqls), [released profile service](https://raw.githubusercontent.com/authorizerdev/authorizer/2.4.4/internal/service/update_profile.go), current API and README. General social unlink, arbitrary two-ID merge, anonymous guest upgrade, crypto-wallet sign-in and classic human support impersonation were not established. Passkey deletion, machine delegation and a signup-method list do not prove those separate operations. Self-deactivation is documented; self-service hard erasure was not.
