## Conflicts and unknowns

- **Lifecycle and dates:** Official repository, README/docs, package/releases and official-domain shutdown/sunset/acquisition searches were checked first. No official ending, acquisition or successor notice was found in this bounded check. Nonarchived status and repository push metadata do not turn an older release into a recent one, guarantee future maintenance or establish a supported-release lifetime.
- **Published version versus latest docs:** PyPI and GitHub latest release are 0.6.3 from October 2023. Current main metadata is 0.7.0.dev and its changelog says unreleased. Main changes include higher minimum requirements, deprecated API/LOGIN_DISABLED removal, and different proxy-address handling. Those are not reported as 0.6.3 defaults. The project's contribution guide explicitly discourages issues asking for release deadlines.
- **Session-cleanup conflict:** Versioned docs describe strong mode as deleting the whole session. Released LoginManager removes only SESSION_KEYS belonging to Flask-Login and requests remember-cookie clearing. Other app session values can remain. F25 keeps both sources and uses code for exact scope.
- **Invalid user-loader ID conflict:** Docs say invalid loader IDs are removed from session. Released _load_user falls back to other methods or anonymous state without an explicit stale-ID removal. Returning None denies that user identity but does not prove a browser/session identifier has been erased. F41 preserves this distinction.
- **Remember/session limits:** Read complete config/utils/login-manager implementation, Flask session source/config/security docs and the alternative-ID/freshness examples. Default remember tokens contain an ID and HMAC signature without an embedded timestamp; browser expiry is not a server-enforced token-age check. Normal Flask signed session age and key fallback behavior differ. Logout clears current-client login keys/cookie, not every device or every copied token. The app must implement persistent revocation/alternative-ID policy as needed; no exploit or browser test was run.
- **Credential and account scope:** Read full docs, release README, public exports, user helpers, loaders and complete release file inventory. Core does not check a password or implement registration, reset, verification, social adapters, MFA, passkeys, organizations or SCIM. The README explicitly warns about shortcuts; its released request_loader accepts an existing email without a password. That example is not a production credential-verification contract or evidence that the core validates passwords. Custom integrations must enforce their own proofs.
- **Business and consumer calculations:** Both fixed business scenarios are unsupported by Flask-Login alone because tenant memberships/invitations/roles and SAML are outside scope. Consumer examples show known software license fees for an explicitly app-provided email/password configuration. Storage, hosting, recovery/security work and delivery remain unpriced. The component is not ranked as a complete zero-cost hosted account product.
- **Export/import/deletion:** Read storage-independent user contract, get_id/user loading, remember/session representation and Werkzeug verification/migration guidance. User profiles, hashes, provider links and passkey/MFA data live in the app/chosen integrations, so formats and migration compatibility cannot be guessed from Flask-Login. Logout is not account deletion, backup erasure or universal signed-session invalidation.
- **Bounded unpublished findings:** Before marking gaps, checked the complete release docs/source tree and relevant implementation. Docs/README/demo do not publish an accessibility assessment; docs/API/request-loader examples and source inventory do not publish a native client matrix. Installation, CI/tox and Flask production deployment guidance do not publish guaranteed hardware/throughput capacity. Docs/README/security pages do not publish independent assurance. Security/contribution/release pages do not publish a formal security response/LTS schedule or commercial support hours/prices. Exact pages are attached to each not_published row.
- **Policy and hosted-only fields:** Read MIT and the named dependency licenses, GitHub security policy/advisory pages, contribution guidelines and separate Pallets security policy. Flask-Login's own policy page says no SECURITY.md is detected; no published advisories is not proof of no vulnerabilities. Pallets' policy for its own projects is not automatically this separate repository's policy. There is no hosted rate card, trial, tenant region, vendor account closure, identity-processing DPA or uptime plan to apply to embedded code; actual infrastructure/identity processors need their own agreements.

It was repeated with package metadata reduced to the relevant publisher fields; docs/policies/package data then read successfully. No field remains check_failed. No failed source was used as fact evidence.
