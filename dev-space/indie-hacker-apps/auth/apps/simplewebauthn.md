## Conflicts and unknowns

- **Node support declarations:** v14 docs and release notes state Node LTS 22+ / Deno 2.4+, and current build configuration sets Node >=22. The published server 14.0.3 npm metadata and actual tarball manifest both say >=20. The tarball was inspected to rule out a metadata-only assumption. These declarations differ; the looser engine declaration does not prove Node 20 is in the actively supported set or that it was tested here.
- **Package retirement:** Homepage copy still mentions a dedicated types package. Current v14 docs explicitly explain its deprecation after v12 and migration to server/browser exports in v13+. The package retirement notice resolves the correct current setup; it is not a shutdown of the passkey libraries.
- **Release versus HEAD:** Latest stable server is 14.0.3 from September 25 and browser 14.0.0 from September 2, 2026. Later October HEAD includes TPM parsing work. Release notes were read through the official release records; latest default-branch code is not presented as an npm release. Server/browser patch numbers need not match.
- **Security notices:** Read current release notes and both linked project advisories. The CRL-cache advisory states affected 14.0.1 and patched 14.0.2. The older trust-anchor advisory states affected <13.3.1 and patched 13.3.2; no additional affected interval is inferred. These are scoped notices about certificate/attestation validation, not a claim that every application using any passkey mode was compromised. No exploit or security scan was run.
- **Authentication versus account management:** Read philosophy, server/browser API exports, integration guide and example server. No password/social login service, email sender, account database, organization model, SAML/OIDC federation, SCIM server or session product was established. Those are outside the two libraries' protocol role, not merely missing enterprise prices.
- **Passkey policy:** Read passkeys guide, generation/verification source, browser methods and capability helpers. Discoverable credentials, Conditional UI, Conditional Create, transports and verification/backup outputs are documented. Generation preferences and verifier enforcement are separate: examples may explicitly disable user verification while verifier defaults require it. A verified point of contact and safe enrollment/recovery policy remain application work.
- **Example/doc age:** Some passkey-guide prose still refers to an older positional autofill argument, while current browser documentation and v14 source use an options object with useBrowserAutofill. Current package API/source is used in this record. Historic OS minimums/quirks are not treated as an exhaustive present-day platform certification; official supported-devices page delegates to an external device-support reference and the library provides runtime feature detection.
- **Origins and native clients:** Read RP/origin sections, cross-origin guide, verification implementation, browser quirks and device guidance. Expected origins/RP IDs and optional top-origin handling need intentional application configuration. Browser/mobile-web support does not establish official Swift/Kotlin/Flutter/React Native client packages or a complete native app/deep-link matrix. No such native package is listed among maintained libraries.
- **Storage and migration:** Read schema/type guidance, custom user IDs, registration/authentication outputs, challenge generation and example state handling. The app owns credential IDs/public keys/counters/transports/user mapping and exports/imports that storage itself. No universal bulk importer, password-hash migration or authenticator-private-key export is supplied. Preserving database records does not make a credential valid under a different RP ID.
- **Deletion, recovery and signals:** Read current sendSignal docs/source, backup-flag behavior and passkey recovery guidance. Signals do not acknowledge final deletion/update by every credential manager. Server record deletion, app-session revocation and user-controlled synced private-key deletion are separate operations. Recovering an account after loss of all authenticators is an app/account-provider feature, not guaranteed by the library.
- **Assurance:** Read FIDO conformance reproduction guide, optional metadata/root settings and maintenance notes. Project claim of conformance self-validation is not an independent audit of an app, a SOC 2 report or a certificate for every supported client. Metadata checks are opt-in and do not automatically implement every relying party's policy.
- **Bounded unpublished findings:** Runtime/install guides, README, example deployment and API/source checks did not yield universal CPU/RAM/user capacity or logins-per-second guarantees. Root/docs, repository tree/templates, releases and advisories did not yield a package-major LTS guarantee, binding patch deadline or guaranteed security response time. The attempted root SECURITY.md was absent; useful public advisories were available. These gaps are recorded as not_published rather than fabricated values.
- **Hosted fields:** No nonexistent hosted-service pricing, seller-country gate, trial/card, dashboard seats, member quotas, regions, retention policy, DPA/subprocessor list, audit plan or availability promise was sought. Those fields are not_applicable. The chosen app host, account system, external services and user credential providers need their own policies.
