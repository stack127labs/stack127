## Conflicts and unknowns

- **Lifecycle checked first:** Read the official site/news, current docs, release notes, package metadata and Codeberg repository metadata; searched official-domain shutdown/sunset/acquisition notices. No whole-project notice found in this bounded search. The Codeberg repository is not archived. The old Read the Docs site still shows 64.3.0 but links to the current docs/source; this is not proof of abandonment. The community discussion mailing list is deprecated, and release notes explicitly removed the nonoperational AngelList provider. Neither notice retires allauth.
- **Current security/maintenance evidence:** The October 30, 2026 65.21.1 release fixes multi-window rate-limit accounting and passkey user-verification enforcement. Earlier October notes include MFA/code/login-flow fixes. This record is not a complete advisory or penetration-test report. Read relevant notes before using an older release; the project-specific security contact is security@allauth.org.
- **No paid feature edition:** Read the MIT license, feature page, funding, sponsors and commercial-support pages. Sponsorship has published optional prices and support benefits, but the feature page says the software feature set is the same. No nonexistent hosted pricing/trial/quota/region/DPA/SLA plan was searched or assigned. Optional support does not make SAML, passkeys, MFA or APIs paid production features.
- **Code-format conflict:** The public feature page says a six-digit OTP for regular login. Current common configuration and pinned code default to eight nonnumeric characters, displayed with a dash; the March 2026 release notes describe the change. F20 preserves both sources and prefers current release/configuration behavior. TOTP's six digits and recovery codes' eight digits are separate values. No silent normalization of all code types was made.
- **Phone support resolved in source:** General account configuration describes emailed login codes and its login-method options omit phone. The dedicated phone guide, pinned form and login-by-code flow explicitly support a phone selection and SMS login delivery. Phone-based code login is therefore recorded as available with the required custom phone storage/SMS hooks. Its login-code timeout is distinct from phone-verification timeout. The project does not supply a phone-number table or choose/pay an SMS sender.
- **Default authentication and safety scope:** Read account/social/MFA configuration and source. Enabling MFA does not force enrollment for every user; default Django admin login bypasses the allauth workflow and needs its own protection. WebAuthn first-factor passkeys require user verification; other WebAuthn MFA defaults to preferred. The default MFA encrypt/decrypt hooks do not encrypt database secrets, so operator encryption/storage/key policy remains relevant.
- **SCIM and organizations:** Read feature table, documentation/module inventory, complete headless API paths, SAML/OIDC docs and advanced-account guidance. No bundled SCIM implementation was found. Invitation handling is explicitly outside scope. A SAML IdP slug, OAuth/OIDC client or Django staff/group is not a complete customer organization with invitations, membership and isolation. Both fixed business scenarios are unsupported by bundled allauth alone.
- **Sessions and native clients:** Read usersessions models/settings, headless browser/app specification and both token strategies. Server-backed sessions, X-Session-Token, optional headless JWTs and outgoing OIDC tokens have different expiration/revocation rules. Stateless headless access-token validation does not immediately revoke tokens at logout by default. No complete native SDK/passkey platform-version matrix was found after reading headless docs, API/specification, WebAuthn docs and browser helper. Generic mobile API support is not proof that every native client/passkey setup works without added integration.
- **Accessibility and assurance:** Read template/design docs, README, feature/site links and official-domain searches. Found shipped translations and customization mechanisms, but no allauth-specific public accessibility conformance report or inspectable independent security audit report. Project statements about commercial use/testing attempts remain project claims. Django's accessibility work is not automatically an assessment of allauth or a final custom frontend.
- **Import/export and erasure:** Read User-related model schemas, password/serialization docs, MFA migration guide, provider-ID migration notices, WebAuthn storage/domain code and model/session deletion behavior. Operator-owned data can be exported, but destination schema/hash support, provider identifiers, RP IDs, custom phone models and encryption keys must be preserved or deliberately migrated. Removing a database user is separate from deleting backups, external messages or authenticator private keys. No all-purpose import/export or retention guarantee was invented.
- **Capacity and support gaps:** Requirements/install/cache/deployment pages do not provide universal hardware sizing or throughput for the scenario user counts. Sponsor/support/security pages do not publish a complete consulting tariff, fixed support hours/response SLA or allauth LTS/backport calendar. These bounded gaps are not_published. No hosting or developer-time estimate was substituted.

Guessed nested phone pages were 404; the actual guide is account/phone.html and its pinned RST source. Guessed MFA upgrade paths were 404; navigation led to mfa/django-allauth-2fa.html. An attempted allauth/usersessions/management/commands/clearsessions.py was absent; the checked UserSession source and Django sessions documentation establish the actual session-management/cleanup boundary. None of those discovery failures is used as proof of a missing feature.
