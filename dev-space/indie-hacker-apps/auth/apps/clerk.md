## Field problems

- **F08/F12/F13:** A monthly active-user input does not usually equal MRU. These baselines deliberately make every user a returning existing user, which resolves it. A different signup/return pattern needs different inputs.
- **F12/F13/F17:** Login method alone does not settle notification/verification volume. The cost section states a no-new-message sub-scenario and keeps the email-heavy total unresolved. The fields should store delivery assumptions next to the subtotal.
- **F14/F15/F16/F27:** “Organization,” “workspace,” “connection” and “seat” describe different objects. Keep customer Organization member caps, developer dashboard seats, subscription scope and SSO/SCIM meters separate.
- **F22/F23/F25/F44/F48:** A simple yes/no loses app-creation dates, opt-in updates and minimum SDK versions. Current passkey/MFA support and old lockout defaults need those conditions.
- **F31:** Supported language tags are useful, but an experimental localization API and hosted-page English limitation should travel with the list. Accessibility marketing is not an audit result.
- **F39/F41:** User export, password-hash export, account merge, credential transfer and deletion are different capabilities. The fields are useful if they preserve those separate values.
- **F42/F43:** The public legal pointer is available while the live subprocessor list was not machine-readable. Keep retrieval failure separate from “not published.”
- **F47/F49:** Availability percentage, service credits, support submission channels and first-response targets must remain separate. A 24/7 contact route does not promise a 24/7 response.
- **F50/counts:** Count source-backed subrows separately from the 50 field IDs. Otherwise a field with one confirmed part can hide missing or conflicting subparts. The count method below makes both visible.
