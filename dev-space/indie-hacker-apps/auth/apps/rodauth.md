## Conflicts and unknowns

- **No unresolved conflicting plan/price claims established.** Core is an MIT library and extensions have their own licences/versions. A future Rodauth 3 default is not a current edition conflict; shipped opt-in features are not a default-enabled hosted product.
- **Latest security evidence takes precedence over older patch headlines:** Read all six official advisories and current release/source. The earlier OTP advisory identifies 2.47.0 as patched for its reported case; the November notice documents a further future-time-step case fixed in 2.50.0. Record the follow-up and rotp >=4 condition rather than calling every OTP drift case fixed by 2.47.0. Other advisories are conditional on their named features/settings. No exploit was executed.
- **Recommended HMAC versus runtime enforcement:** Read base/require_hmac_secret implementation and README security/recommendations. Core recommends trusted domain/base_url, already-logged-in handling and HMAC configuration; some feature docs call HMAC required. In 2.50.0 missing-recommended-configuration handling can warn instead of raising at startup. Future Rodauth 3 enforcement must not be assigned to current code. App security still depends on actual configured secrets and routes.
- **Sessions and offboarding:** Read core cache/session design, session_expiration, active_sessions, single_session, remember, JWT and refresh docs/source. Authentication state can remain cached outside the session where an account changes. Call the appropriate checks to enforce revocation. The 30-minute/1-day session_expiration defaults differ from the 1-day/30-day active_sessions defaults. JWT logout alone does not revoke old JWTs; refresh rotation alone does not expire old access tokens.
- **Remember versus refresh:** Remember login is separately enabled and loaded by app routing. Forgetting one browser cookie is different from deleting its shared remember key. Refresh/logout requires the actual token or all as documented. Logged-in changes do not automatically remove every refresh key; active-session enforcement is the documented approach for stronger revocation.
- **MFA, recovery and WebAuthn:** Read factor docs, defaults, browser code and enforcement guide. require_login is weaker than requiring MFA. SMS delivery is custom, and SMS-primary-MFA remains a second check after login. Recovery codes are plain text/viewable, single-use and not automatically replenished by default. Generic WebAuthn and autofill use different resident-key/user-verification options. Configure recovery/credential removal and origin/RP identity; no native-device matrix or unrelated-domain migration promise was established.
- **Social linking trust:** Read released rodauth-omniauth docs, package/licence and named provider strategy sources. Default identity lookup links by email and can verify matching accounts; app must trust the provider's email ownership semantics or override matching/verification. The extension states that signed-in connecting/removing identities is not built in. Provider UID persistence is not a last-login-method safeguard or customer membership model.
- **Business standards and unsupported cost baselines:** Read official external-feature index, social plugin, primary GitLab OAuth extension/tagged gemspec and SAML/OIDC strategy docs/package metadata. Client/SP, authorization-server/OP and SAML bearer assertion grant are different roles. No complete organization membership/invitation/role product or SCIM behavior was found. Both business baselines need app work/additions before pricing a usable system.
- **SCIM not published:** Complete released source inventory, core/external index, social and OAuth extension docs and official-domain SCIM search did not establish a core or documented turnkey Rodauth directory-sync product. This is a bounded finding, not proof that no other Ruby library can be connected.
- **Accessibility/native support not published:** Checked core UI/templates/base methods, JSON/WebAuthn/browser JavaScript, API/integration docs and official-domain accessibility search. No product conformance report or native SDK/platform matrix found. API availability, labels and conditional-mediation browser checks are narrower evidence.
- **Operations/sizing not published:** Checked README schema/database-role/function setup, migration helpers, feature prerequisites, runtime policy and CI. No universal CPU/RAM/MAU/requests-per-second guarantee or complete deployment-independent restore recipe found. The recommended restricted app role is an explicit design condition; it may not be possible on every managed database.
- **Export/import limitations:** Read recommended schema/permissions/functions, configurable columns, programmatic account creation, hash algorithm/pepper migration and identity/factor storage. Ordinary app-role access cannot read password hashes in the recommended setup. Privileged export tooling and target compatibility are required. Database ownership does not imply an automatic vendor-compatible user/factor/session migration.
