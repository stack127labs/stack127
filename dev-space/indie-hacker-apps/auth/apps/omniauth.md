**Production scope:** [Core only bundles the insecure Developer strategy](https://raw.githubusercontent.com/omniauth/omniauth/v2.3.1/lib/omniauth/strategies/developer.rb); it must not be used for production. Real provider strategies are separate. OmniAuth returns identity data to the app callback and [deliberately does not implement local User/account/session management](https://raw.githubusercontent.com/omniauth/omniauth/v2.3.1/README.md). Checked date: **2026-11-05**.

## Conflicts and unknowns

- **Current release conflict:** Checked publisher package metadata, stable tag, README/changelog and GitHub latest-release API. API's 2.1.4 release object is stale relative to 2.3.1 publisher/tag evidence; it is not proof of retirement or an unofficial package. Current app row status remains consistent with repository activity.
- **Host advisory metadata conflict:** Read full official advisory, 2.2 security changelog and 2.3.1 host/request/callback implementation. Advisory displays None for patched versions, while newer code offers fixed host/allowlist mitigation. The default allowlist is nil and unset configuration warns rather than rejects all unknown hosts. No unconditional “upgrade fixes every host injection” conclusion.
- **CSRF wiki conflict:** The mitigation page says “only accept get requests” in one sentence while its own snippet uses [:post]. Current code and the rest of the guide use POST and an authenticity-token validator. Its date/version header and old FAQ examples should not substitute for released behavior. Do not silence a warning or globally enable GET as a purported fix.
- **Rails validator scope:** Read tagged core README/token protection and current Cookpad component docs/code/package/licence. Built-in protection can be configured for the app's session token key; the separate Rails-aware verifier remains an alternative. Compatibility depends on real token/session handling, not simply installing a library. No request test was run.
- **Account boundary:** Read complete core inventory, strategy callback/auth-hash code and app-integration/wiki examples. Core sets provider data in Rack env; it does not create local users, persist passwords, establish authenticated app sessions, ban/delete users or expose an account admin API. Those are actual application responsibilities.
- **Password strategy scope:** Read omniauth-identity 3.2.1 strategy/model/secure-password/ORM interfaces, metadata and actual MIT terms. It adds login/registration with app persistence and password_digest handling; it is not a bundled core password method or a complete reset/verification/MFA/account-center product. Optional package support/funding offers do not become OmniAuth core pricing.
- **Provider-specific evidence:** Independently read Google, GitHub, Apple and Microsoft strategy-owned docs and fresh publisher metadata. Required credentials, scopes, protocol/dependency choices and email trust differ. No fixed provider-count promise or universal native/device matrix is based on the community strategy index. Named plugin dependency ranges are not validation of every locked app combination.
- **SSO role boundary:** Read SAML/OIDC strategy docs, metadata and licences. These are service-provider/relying-party clients; core is not a SAML IdP or OAuth/OIDC authorization server. Configurable logout endpoints still need app/IdP setup and local-session cleanup. A free SAML strategy does not supply organization memberships, invitations or member roles.
- **Organization/SCIM unknowns:** Complete core tree, overview, schema/strategy/setup guides and official-repository SCIM search did not establish a bundled customer-tenant or directory-sync product. Per-request credentials and identity linking are different. Both fixed business baselines are unsupported by OmniAuth alone; a complete custom app could add them but must be selected/built and priced.
- **Session/transaction/token distinctions:** Read core session requirement, keyed sign-in storage, callback consumption and OAuth2 1.10.0 implementation. Five remembered transactions is not a five-user/device cap or a TTL. App login expiry and device revocation are independent. Provider access/refresh tokens may be returned; callback refresh of an already-expired token is not an operated long-lived account session service.
- **Cookie/callback conditions:** Core README documents session continuity and SameSite differences between top-level GET callbacks and cross-site form POST. Source/provider callback settings must be reviewed together. Old FAQ's callback-CSRF skip example is not blanket permission to remove protocol state/signature checks.
- **Linking/import/export/deletion:** Read auth-hash schema, normalization code, multi-provider User/Identity recipe and optional password model. Core exports callback attributes, not a complete directory or upstream passwords/factor private keys. App must preserve provider/uid/issuer context, implement linking/unlinking/last-method policy, map imports and handle deletion/associated records/backups. Old wiki example acknowledges data-loss/dangling-identity problems; no secure automatic merge is claimed.
- **Accessibility/native evidence not published:** Checked README, form/Developer helpers, strategy/integration/API/provider guides, full core inventory and official-repository accessibility search. No core conformance assessment or supplied native/mobile SDK compatibility matrix found. A helper form, upstream IdP UI or generic OAuth/PKCE path is narrower evidence.
- **Operations/capacity not published:** Checked installation/prerequisites, strategy guidance, semantic-versioning/changelog and CI. No universal hardware, MAU sizing, throughput promise or deployment-independent restore procedure found. Core has no database, so actual identity/account/session stores determine much of operation.
- **Privacy/audit/support:** No hosted OmniAuth identity processor or region selector exists in this library offer. MIT governs code use; app and real service providers supply processing/retention policies. Logger/hooks are not a managed audit store. Checked overview/security/strategy/maintenance and funding sources did not establish core independent attestation, exact LTS/end dates or paid response/fix guarantees.
- **Version support limits:** SECURITY.md explicitly marks 2.0.x through 2.3.x supported and <=1.9.1 unsupported; 1.9.2 is unlisted. No automatic backport/time guarantee inferred. CI matrix is configuration evidence, not executed checks or proof old Ruby versions still receive upstream fixes.

OIDC licence is LICENSE.txt. Large strategy-index retrieval was narrowed to relevant entries; plugin-owned source/metadata, not that community index, establishes plugin facts. Every supporting table URL was successfully read.
