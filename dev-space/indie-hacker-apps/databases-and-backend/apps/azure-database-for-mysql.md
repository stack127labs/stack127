# Azure Database for MySQL

## Shutdown, sunset and acquisition check

Checked first on 2026-11-05. Flexible Server remains generally available in the [official overview](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/overview); no complete-service shutdown or acquisition notice was found in the inspected product, lifecycle and current-release pages. This is a bounded notice search, not a promise about future operation.

- **Single Server retired September 16, 2024.** The successor is Flexible Server. Keep the retired deployment out of current pricing comparisons. [Microsoft-authored retirement notice](https://techcommunity.microsoft.com/blog/adformysql/azure-database-for-mysql---single-server-retirement---key-updates-and-migration-/4055198) (checked 2026-11-05).
- **Older engines have paid-support dates.** Azure standard support for MySQL 5.7 ended September 30, 2026; automatic Extended Support started October 1, 2026 and ends March 31, 2029. MySQL 8.0 standard support ends January 31, 2027; Extended Support runs February 1, 2027 to May 31, 2029. These are Azure dates, not the community retirement dates. [Version support policy](https://learn.microsoft.com/en-us/azure/mysql/concepts-version-policy) (checked 2026-11-05).
- **Innovation Preview servers are automatically removed after 30 days.** They lack automated backups, HA and read replicas. This is not the lifetime of an ordinary GA server. [Version policy, Innovation release](https://learn.microsoft.com/en-us/azure/mysql/concepts-version-policy) (checked 2026-11-05).
- **Long-term backup retention Preview is paused for new configuration.** Microsoft says not to configure new backups until further notice; existing backup data remains available for restore. The up-to-10-year description is not an unrestricted current offer. [Backup and restore, Long-term retention](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-backup-restore) (checked 2026-11-05).
- **TLS 1.0/1.1 are retired.** Forced upgrade enforcement began August 31, 2025; clients need supported encrypted connections. [TLS configuration notice](https://learn.microsoft.com/en-us/azure/mysql/security/security-tls) (checked 2026-11-05).

## Cost examples — our calculation

These are public retail calculations checked on 2026-11-05, not Microsoft quotes. Region: East US (`eastus`); currency: USD; normal consumption pricing; 730 hours when always on. Use a GA MySQL version still in standard support, no discount commitment, Basic support, no Accelerated Logs, Reader Endpoint or optional private-network resources. No workload was run.

Rates come from the [public Retail Prices API query](https://prices.azure.com/api/retail/prices?%24filter=serviceName+eq+%27Azure+Database+for+MySQL%27+and+armRegionName+eq+%27eastus%27+and+priceType+eq+%27Consumption%27&currencyCode=%27USD%27), cross-checked against [MySQL pricing and billing FAQ](https://azure.microsoft.com/en-us/pricing/details/mysql/). The API response had 83 records and no next page. Only named Flexible Server meters were selected; retired Single Server records were excluded. B1MS is a per-server-hour meter; General Purpose Ddsv4 is a per-vCore-hour meter. Full-hour rounding applies to compute.

### Inputs and unit limits

- Let `G` be average provisioned storage in **billable GB-months**, `Q` consumed autoscale LRS physical I/O operations, `B` active-server backup storage in billable GB-months, and `E` internet transfer charged at the first paid North American tier. The basic non-HA formula is `billed_compute_hours × server_hour_rate + 0.115G + 0.20Q/1,000,000 + 0.095 × max(B − G, 0) + 0.087E`.
- The service minimum is **20 GiB** in the [capacity table](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-service-tiers-storage); the original-storage API meter says **GB/month**. The inspected pages did not define their equivalence. Do not silently replace one with the other. For a numerical illustration below, assume the invoice reports **G = 32 GB-months**. This is a stated billing input, not a claim that 1 GB of application rows is the provisioned amount, or that a portal choice of 32 GiB necessarily bills 32 decimal GB.
- `Q` is not logical SQL reads plus writes. Caches, indexes, transaction logs and background work affect physical I/O. Autoscale is chosen for these formulas so no undocumented included provisioned-IOPS allowance is assumed. With pre-provisioned IOPS, replace the consumed-I/O term with the actual applicable provisioned/additional-IOPS bill; the published additional rate is USD $0.05/IOPS-month. See [the IOPS-mode guide](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-storage-iops).
- [Bandwidth pricing](https://azure.microsoft.com/en-us/pricing/details/bandwidth/) supplies a shared first 100 GB/month internet-egress allowance. For this route, `E = max(total_eligible_egress − 100, 0)` within the first paid tier. Five GB of this app’s transfer costs $0 only if enough allowance remains. If already exhausted, `5 × $0.087 = $0.435` before tax. This is exact arithmetic, not silently rounded to cents.
- [Backup documentation](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-backup-restore) says the active free-backup allowance is 100% of primary provisioned storage. Neither 1 GB of live rows nor a seven-day window fixes `B`. The original-storage GB/GiB ambiguity, backup changes and I/O volume prevent a complete workload total. Taxes, contract pricing, monitoring integrations, cross-region traffic and optional resources are additional where applicable.

### 1. Small SQL app

Inputs: one production database; 1 GB logical data retained for the month; 100,000 reads and 20,000 writes; 10 peak connections; 5 GB internet transfer; 730 running hours.

**Production-oriented variant:** [Microsoft’s tier guide](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-service-tiers-storage) recommends General Purpose for this class of workload. Use documented D2ds_v4, 2 vCores/8 GiB physical memory, and the East US Ddsv4 rate of $0.0855/vCore-hour.

- Compute: `730 × 2 × $0.0855 = $124.83`.
- Illustrative provisioned storage: `32 × $0.115 = $3.68`.
- Known conditional subtotal: `$124.83 + $3.68 = $128.51/month`.
- Complete expression: `$128.51 + $0.20Q/1,000,000 + $0.095 × max(B − 32, 0) + $0.087E`, plus omitted optional resources/taxes. Actual required compute and billable capacity are not established by query counts alone.
- Sensitivity only: if measured physical I/O were 120,000 operations, its cost would be `120,000/1,000,000 × $0.20 = $0.024`. The given 120,000 logical reads/writes do **not** establish that measurement.

**Burstable comparison:** B1ms compute is `730 × $0.017 = $12.41`; with the same illustrative storage, `$12.41 + $3.68 = $16.09`, before I/O/backup/transfer. It has CPU-credit limits and Microsoft does not recommend it for production. It is a cost illustration for an intermittent/dev workload, not the selected production configuration or a capacity guarantee.

**Eligible free-resource variant:** the [12-month offer](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/overview) covers 750 B1ms hours, 32 GB storage and 32 GB backups per eligible month. Assuming this server’s eligible meter usage stays within those exact limits, `max(730 − 750, 0) × $0.017 = $0` compute and the included storage/backup components contribute $0. No specific free physical-I/O allowance was established; a complete recurring bill remains unknown. Free production permission is unresolved, so this is not a free-production recommendation. The separate [$200 credit](https://azure.microsoft.com/en-us/pricing/offers/ms-azr-0044p) applies only within the initial 30 days and does not recur every month.

**Backup variant:** for an active server with `G = 32` and `B = 40` billed GB-months, excess backup is `(40 − 32) × $0.095 = $0.76/month`. Geo redundancy stores two copies; it cannot be priced from logical row size alone.

**Same-zone HA variant:** choose a supported General Purpose pair and the original LRS storage meter. Known allocated components: `2 × $124.83 + 2 × 32 × $0.115 + 72 × $0.05 = $260.62/month`. This includes the FAQ’s extra 72 provisioned IOPS. It excludes any other configured IOPS, actual excess backup, transfer and optional resources; it is not an all-in HA quote. Zone-HA/ZRS must use its own storage/IO rates and configuration. See [HA architecture](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-high-availability) and [HA billing FAQ](https://azure.microsoft.com/en-us/pricing/details/mysql/).

### 2. Full app backend

Inputs: the SQL scenario plus 1,000 monthly active app users, 1 GB independent files, 100,000 file reads, 10,000 uploads, 20 GB total internet transfer and 10,000 short application-function calls. To make the function assumption explicit, use 1 second and 0.5 GB memory per call; no external function product is selected.

Formula: `SQL component + app-auth service + file storage/requests + function host/invocations + applicable networking`. The SQL component above is incomplete. [MySQL service scope](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/overview) does not establish bundled app-login, file delivery or function allocations. Entra database authentication is not a free 1,000-MAU app service. Complete total: **unknown; workload does not fit this product alone**. If the 100 GB transfer pool is exhausted, 20 GB at the stated route is `20 × $0.087 = $1.74`; otherwise enough remaining allowance could cover it. No external Azure service is silently included at zero.

### 3. Small file store

Inputs: 100 GB average hot objects for 30 days, 100,000 writes, 1 million reads and 100 GB internet transfer, retained for the month.

Formula: `independent-object GB-months × object rate + write/read requests + delivery`. No applicable object tariff or file API is established by [MySQL pricing](https://azure.microsoft.com/en-us/pricing/details/mysql/). Database storage is not a substitute for a bucket quote. Complete total: **not applicable to MySQL alone; unknown until an object service is selected**. The $0.115 database-storage meter is not applied to these files.

### 4. Small vector search app

Inputs: 100,000 vectors, each with 1,536 float32 values and 1 KiB metadata; 100,000 searches, 10,000 updates and 5 GB internet transfer.

Raw payload, **our calculation**: `100,000 × (1,536 × 4 + 1,024) = 716,800,000 bytes = 0.7168 decimal GB`. This excludes rows, indexes, ANN structures, replicas and logs. The inspected [version policy](https://learn.microsoft.com/en-us/azure/mysql/concepts-version-policy), [limits](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-limitations), [2026 releases](https://learn.microsoft.com/en-us/azure/mysql/whats-new/whats-new-2026) and pricing did not establish an included native vector-search contract, dimensions or embedding/reranking tariff for this offer. Azure SQL/PostgreSQL/HeatWave capabilities are not substituted. Formula: `database resources + a verified search implementation/index overhead + model fees`; total **unknown**. Raw bytes do not establish required provisioned capacity or query CPU.

### 5. Small job workload and retry/wait variant

Inputs: 10,000 jobs, one active second each, target 0.5 vCPU/0.5 GB RAM, peak five concurrent jobs, no retries or waits in the base case. Active work is `10,000 × 1 = 10,000 seconds`.

[event_scheduler](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/concepts-server-parameters) runs scheduled SQL in the database; this offer does not supply a separately selectable 0.5-vCPU worker. If all work can be expressed in SQL, it shares the whole server and its I/O. Formula: `provisioned server-hour cost + storage + actual I/O/log growth`; **not** `10,000 seconds × a serverless worker rate`. A worker for general application code would need another host. Complete requested-worker total: **unknown**.

Variant: assume 10% of originals get one extra one-second execution, and each original also spends five seconds waiting. Active work becomes `10,000 + 1,000 = 11,000 seconds`; added wait is `10,000 × 5 = 50,000 seconds`. That is 61,000 aggregate active-plus-wait seconds, not necessarily elapsed server time because runs may overlap. SQL waits/retries do not remove allocated server charges; external worker wait/retry pricing and delivery guarantees remain unspecified.

### 6. Idle project

Inputs: retain the SQL scenario’s 1 GB logical data, zero app queries and jobs, and the same illustrative `G = 32` billable GB-months.

- **Left running 730 hours:** the same $128.51 General Purpose compute/storage subtotal, or $16.09 for B1ms, still applies before actual backup and background I/O. No automatic idle-query sleep rule was established.
- **Manually stopped:** compute is not charged for stopped time; storage/provisioned IOPS persist. The [stop/start guide](https://learn.microsoft.com/en-us/azure/mysql/flexible-server/how-to-stop-start-server-portal) auto-starts after **30 continuous days (720 hours)**, so one stop does not span a 730-hour month.
- Conditional illustration: stop at the start, run for exactly 10 billed hours after automatic start, keep the assumed storage, and use no committed discount. General Purpose compute/storage is `10 × 2 × $0.0855 + 32 × $0.115 = $5.39`; B1ms is `10 × $0.017 + 32 × $0.115 = $3.85`. Startup timing, hourly rounding, IOPS and backup charges can change the actual bill.
- **Backup conflict:** pricing would charge only excess backup above the normal allowance while stopped; the backup FAQ says no free backup allowance while stopped. Let `B_s` be retained backup usage in billable GB-months for the stopped portion. The latter adds `$0.095B_s`; the former allows a capacity deduction. Neither a precise $0 idle bill nor a single exact stopped total is supported.
- **Eligible free month:** the temporary monthly B1ms/storage allowances may cover their eligible components, but the backup conflict and missing physical-I/O allowance prevent a complete guaranteed $0 result. After 12 months, ordinary paid meters apply.
