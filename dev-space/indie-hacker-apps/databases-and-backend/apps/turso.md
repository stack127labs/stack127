## Operating status and notices

Checked **2026-11-05**. On **2026-10-02**, Turso announced it is being acquired by Supabase. The notice explicitly says Turso databases, APIs and workflows continue and Turso Database remains open source/actively developed. No overall shutdown/sunset notice was found in the official announcements and current docs checked. Source: https://turso.tech/blog/turso-is-joining-supabase, “What this means for Turso users.”

Earlier changes still matter: **2025-01-21** withdrew geographical edge replicas, hosted ATTACH and Multi-DB Schemas for new users, while preserving existing paid usage. That notice also renamed the rewrite from Limbo to Turso and distinguished the proprietary new Cloud server from open-source engines/libSQL server. **2026-05-03** removed paid active-database limits. Sources: https://turso.tech/blog/upcoming-changes-to-the-turso-platform-and-roadmap, https://docs.turso.tech/features/data-edge.md, https://docs.turso.tech/features/attach-database.md, https://docs.turso.tech/features/multi-db-schemas.md, https://turso.tech/blog/turso-now-includes-unlimited-databases-for-everybody.

Cloud **libSQL** is the established production offering; the newer **Turso engine on Cloud is early preview**. AgentFS is beta. Current Turso changelog opens with version 0.8.0 dated 2026-09-28. Engine features, SDK support and Cloud deployment stage differ. Sources: https://docs.turso.tech/turso-cloud.md, https://docs.turso.tech/libsql.md, https://docs.turso.tech/agentfs/introduction.md, https://docs.turso.tech/tursodb/changelog.md.

## Cost examples — our calculation

All rates below are USD before tax, checked **2026-11-05**. Use **AWS us-east-1** as the deployment example; the pricing table does not publish a separate multiplier for that region. Organization allowances are shared across databases. These are our calculations, not vendor quotes. Exact top-up blocks, storage sampling and GB denominator remain unpublished in the pages checked; byte conversions below explicitly use decimal GB for the scenario rather than claiming Turso defines GB that way. ### Small SQL app and idle database

Inputs: one production database; **1 GB billed database space** for a month, including indexes; 100,000 reads and 20,000 writes; 10 peak connections; 5 GB ordinary internet response transfer. Request counts are not necessarily billable row counts. Let **R** be billed row scans, **W** billed row writes including indexes/aborted writes, **S** billed storage GB and **T** billed sync GB. No embedded sync is assumed in this first example, so T = 0; ordinary SQL responses are not silently counted as sync. Ten-connection eligibility cannot be guaranteed from an unpublished hosted connection ceiling.

| Path | Formula — our calculation | Result and limits |

| Eligible Free | Subscription USD 0, if S ≤ 5, R ≤ 500,000,000, W ≤ 10,000,000 and T ≤ 3 | Known published subscription/usage charge **USD 0** if those conditions hold. 100,000 read requests alone do not prove R. The 5-GB ordinary internet-transfer tariff is unresolved, so a guaranteed all-in total is **incomplete**. |
| Normal monthly paid path, Developer | `USD 5.99 + 0.75×max(0,S−9) + max(0,R−2,500,000,000)/1,000,000,000 + max(0,W−25,000,000)/1,000,000 + 0.35×max(0,T−10)` | For 1 billed GB and row usage inside Developer quotas, known charge **USD 5.99/month**, plus any unresolved ordinary transfer charge. | Idle Free, same 1 GB | Zero SQL work/sync and retained size under 5 GB | Published-meter charge **USD 0**, but Free databases archive after **10 days**; manual unarchive is documented and maximum archived retention is not established. |

### Small vector-search app

Inputs: 100,000 vectors; 1,536 float32 values and 1 KiB metadata each; 100,000 searches, 10,000 updates and 5 GB ordinary internet response transfer.

Raw payload = `100,000 × (1,536×4 + 1,024) = 716,800,000 bytes`, or **0.7168 decimal GB**. This excludes row/page overhead, extra columns and every vector/index copy. Source for float32 storage and index formula: https://docs.turso.tech/features/ai-and-embeddings.md; newer engine search behavior: https://docs.turso.tech/guides/vector-search.md.

- **New Turso engine, full-scan illustration:** if each search visits all 100,000 rows, `100,000 searches × 100,000 rows = 10,000,000,000 billed row reads`. This exceeds Free's 500 million reads. Developer's known read overage is `(10,000,000,000−2,500,000,000)/1,000,000,000 × USD 1 = USD 7.50`; **USD 5.99 + USD 7.50 = USD 13.49/month** before update-related scans/writes, excess actual storage and unresolved ordinary transfer/model costs. Scaler's 100-billion-read allowance contains that read component but has a USD 29 base. These are conditional scans, not measured query performance. Sources: https://docs.turso.tech/guides/vector-search.md, https://docs.turso.tech/help/usage-and-billing.md, https://turso.tech/pricing?frequency=monthly.
- **libSQL DiskANN storage illustration:** choose **M = 32 neighbors**, float32 neighbor storage, with no compression. This is our chosen configuration, not the documented default. Vendor approximation: `N×(Storage(vector)+M×Storage(neighbor))`. Substituting gives `100,000×(6,144+32×6,144) = 20,275,200,000 index bytes`; add 716,800,000 table-payload bytes = **20,992,000,000 bytes**, about **20.992 decimal GB** before other overhead. Real billing size must be measured. If S were exactly 20.992 billed GB for a month, Developer storage excess would be `(20.992−9)×USD 0.75 = USD 8.994`; base plus that component is **USD 14.984**, or **USD 14.98 rounded to cents**, before queries/transfer/other costs. Scaler's 24-GB allowance would contain that illustrative size, but no complete comparative total is possible without ANN query/update work.
