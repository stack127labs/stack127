## Cost examples — our calculations

Checked 2026-11-04. These are our calculations, not vendor quotes, benchmarks or suggested host sizes. Baseline: self-hosted **SQLite mode**, one running TrailBase instance and persistent storage in **Frankfurt, Germany**, chosen only as a scenario location. TrailBase does not sell a Frankfurt region plan. No actual host/provider is selected. Experimental PostgreSQL would add its own database service/operation cost. [Deployment model](https://trailbase.io/getting-started/install/), [Production responsibilities](https://trailbase.io/documentation/production/), [Experimental PG scope](https://github.com/trailbaseio/trailbase).

**Software-license charge: 0**, under the published royalty-free OSL grant and its conditions. This is not an included infrastructure allowance. A general complete-cost formula is:

`0 software fee + host compute + database/file storage + backups + network + email/model/other providers + any operations/support charge = unknown total.`

The host may bundle some of those components; avoid billing the same included disk/bandwidth twice. No per-request, GB-second, MAU or GB price is invented for the software. There is no separate normal paid TrailBase tier to calculate after a hosted free allowance expires; the software-use grant remains the same. A negotiated license exception or third-party managed hosting would be a different quote. [Governing license](https://trailbase.io/license/), [Licensing/exception contact](https://github.com/trailbaseio/trailbase), [Local or S3 storage](https://trailbase.io/documentation/apis_record/).

### 1. Small SQL app

Inputs: one production SQLite database, **1GB stored for the month**, 100,000 reads, 20,000 writes, ten peak connections, 5GB internet transfer and **730 server hours if kept running**.

Formula: `0 software fee + 730 × chosen hourly host rate + provisioned persistent disk + 5GB × applicable internet rate + backup costs`. **Result: software fee 0; complete recurring total unknown.** Indexes, WAL, logs, sessions, snapshots and working space can make disk needs greater than 1GB. Request counts do not determine CPU/memory or a safe server size. Ten HTTP clients are not ten purchasable database connection slots. No claim that a particular low-cost host meets the load. [Royalty-free grant](https://trailbase.io/license/), [Deployment/monitoring/recovery](https://trailbase.io/documentation/production/), [API constraints](https://trailbase.io/documentation/apis_record/), [WAL configuration](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/extension/src/lib.rs).

Backup variant: explicitly enable the periodic job or arrange another schedule; it is disabled by default. Default retained snapshot **count** is five, but exact bytes depend on database size at each run, and periodic backups are not managed PITR. Add independent off-site storage and restore/transfer costs. A HA or continuous-backup variant needs a separate system/host design; no native vendor replica tariff can be added. [Release backup default/schedule](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/core/src/scheduler.rs), [Copied database files](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/core/src/backup.rs), [Snapshot-window setting](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/core/proto/config.proto), [External recovery suggestion](https://trailbase.io/documentation/production/), [PITR/distribution status](https://trailbase.io/reference/roadmap/).

### 2. Full app backend

Inputs: same database/read/write/connection scenario, plus 1,000 MAU, 1GB uploaded files, 100,000 file reads, 10,000 uploads, **20GB total internet output**, and 10,000 short custom calls. For comparison, assume each call takes **one second** and targets a **128MB working set**; this is a demand assumption, not a selectable TrailBase function allocation or a published billing unit.

Formula: `0 software fee + shared host allocation + database/1GB-file storage + 20GB network + database and file backups + SMTP/provider use`. **Result: complete total unknown.** Included auth/APIs/WASM do not add TrailBase MAU or invocation fees, but all work consumes the same server resources. SMTP message counts/provider are unspecified; OAuth may require external setup. One thousand MAU does not price those providers or validate capacity. The default HTTP dispatcher timeout is 20 seconds, but that does not guarantee a particular 128MB workload succeeds. [Authentication flows](https://trailbase.io/documentation/auth/), [SMTP/deployment](https://trailbase.io/documentation/production/), [File storage](https://trailbase.io/documentation/apis_record/), [Custom handler model](https://trailbase.io/documentation/apis_js/), [Dispatcher default](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/wasm-runtime-host/src/http_runtime.rs).

Uploaded file bytes require a separate backup from the database snapshots. Choosing an S3 bucket changes the formula to include its own capacity, requests and network, and potentially a second server-to-bucket data path. [Database-only backup implementation](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/core/src/backup.rs), [S3 integration](https://trailbase.io/documentation/apis_record/).

### 3. Small file store

Inputs: **100GB average ordinary file storage for 30 days**, files retained all month, 100,000 writes, 1M reads and 100GB internet output. Occupancy arithmetic = `100 × 30 = 3,000 GB-days` (**our calculation**, not a TrailBase meter).

Local-filesystem formula: `0 software fee + running TrailBase host + provisioned disk for 100GB objects and metadata + 100GB network + independent file backups`. **Total unknown.** No request allowance makes the 1.1M operations free of host I/O/CPU work.

External-S3 variant: `0 + TrailBase host + bucket capacity + backend requests + bucket/host network + backups`. If each application write/read mapped to one backend PUT/GET, request inputs would be 100,000 PUT and 1,000,000 GET. That mapping is only an assumption: retries, multipart, metadata and caching can change counts. Rates, class minimums, early-deletion conditions and provider rounding are unpriced, so no exact total. TrailBase's configurable HTTP request size must also suit the actual file sizes/proxy path; it is not a giant-object upload guarantee. ### 4. Small vector search app

Inputs: 100,000 vectors × 1,536 float32 values, 1KiB metadata each, 100,000 searches, 10,000 updates/month and 5GB output.

Raw float payload = `100,000 × 1,536 × 4 = 614,400,000 bytes`. Metadata = `100,000 × 1,024 = 102,400,000 bytes`. Sum = **716,800,000 bytes = 0.7168 decimal GB**. This is our raw-size calculation, not SQLite file or index size. Add row/primary-key/header, encoding, index, WAL, logs, stored source text and backups.

Formula: `0 software fee + host sufficient for chosen vector query/index + actual SQLite disk + 5GB network + backups + embedding/reranking service`. **Total and indexed-workload fit unresolved.** The official coffee example uses four hand-selected numeric features and exact distance ordering; it does not prove this high-dimensional workload fits a particular index/host. No embedding-model/token price or free hosted AI quota established. ### 5. Small job workload and retry/wait variants

Fixed comparison demand: 10,000 jobs/month, one active second/job, **0.5 vCPU and 0.5GB RAM** where that allocation exists, five concurrent jobs, no retries/wait. TrailBase does not sell a per-job 0.5-vCPU/0.5GB shape. Its embedded runtime and database share the host; resource sufficiency must be verified for the chosen process/container/host.

Our resource arithmetic, **not billable units**:

- Active job time = `10,000 × 1s = 10,000 job-seconds`.
- At the hypothetical 0.5-vCPU allocation, demand = `10,000 × 0.5 = 5,000 vCPU-seconds = 1.3889 vCPU-hours` (rounded to four decimals).
- Hypothetical memory occupancy = `10,000 × 0.5 = 5,000 GB-seconds`.
- Five overlapping jobs would request **2.5 vCPU and 2.5GB** before server/database/runtime overhead, assuming each actually uses the full stated allocation.

Cost formula: `0 invocation/software charge + host allocation + stored job state/logs + network + backups/external services`. **Complete total unknown.** A continuously allocated server is not billed only for 1.3889 demand-hours, and runtime timeout is not durable queue delivery. [Execution model](https://trailbase.io/documentation/apis_js/), [Dispatcher/host execution](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/wasm-runtime-host/src/http_runtime.rs), [Scheduled-job metadata](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/wasm-runtime-common/src/manifest.rs), [Actual scheduler semantics](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/core/src/scheduler.rs).

Retry variant (our assumption, not built-in retry policy): 10% execute once more → **11,000 attempts**, **11,000 active job-seconds**, **5,500 hypothetical vCPU-seconds**, **5,500 GB-seconds**. Software invocation charge remains 0; infrastructure/log/side-effect work rises.

Wait variant: add two seconds asynchronous waiting inside each of those 11,000 attempts. Held-memory time becomes `11,000 × 3s × 0.5GB = 16,500 GB-seconds`, while assumed active CPU demand remains **5,500 vCPU-seconds**. No fabricated GB-second rate applied. Persisted delayed work could avoid keeping an execution open, but requires an application design or another queue; native durable queue capability is still a roadmap item. [No immediate retry/catch-up loop](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/core/src/scheduler.rs), [Per-job timeout configuration](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/crates/wasm-runtime-guest/src/job.rs), [JavaScript job registration](https://raw.githubusercontent.com/trailbaseio/trailbase/v0.35.9/guests/typescript/src/job/index.ts), [Message queue status](https://trailbase.io/reference/roadmap/).

### 6. Idle project

Retain the full-backend **1GB database + 1GB uploads**, zero user requests/functions for a month. Software fee stays 0. If kept running: `0 + 730 server hours + retained volumes + backups + any external minimums`; **total unknown**. Maintenance, log/anonymous/session cleanup and backups can still run despite zero user traffic.

If the operator stops the process, jobs stop too; disk, snapshots and remote buckets can keep billing under their own provider terms. There is no TrailBase managed auto-pause, immediate wake promise or a new zero-dollar storage entitlement. Default log cleanup is seven-day retention checked periodically; deleting older logs is not deleting backend data. ## Field problems

- Hosted free-plan quotas, billing meters, idle pause, spend caps and object minimum charges do not apply directly to free self-hosted software. Their rows explain the scope instead of assigning zero infrastructure cost or unlimited capacity.
- SQLite and experimental PostgreSQL must stay separate. In particular, SQLite backup code does not establish PostgreSQL recovery support.
- Backup retention needs both **snapshot count** and schedule; “days retained” alone would misstate this product. Database and uploaded-file protection must also stay separate.
- The file-size field mixes HTTP request limits, multipart form upload and object-store resumable protocols. Only the documented/configured limit can be recorded without guessing the rest.
- Embedded WASM jobs are not a managed per-invocation machine product or a durable queue. Helper timeouts, memory reservations and latest in-memory execution state should not become paid resource limits or replay guarantees.
- Vector fields are optional here but useful because an official example exists. Its four-dimensional feature query does not prove the standard 1,536-dimensional indexed workload fits. Keep the cost example incomplete.
- C22 describes the quality of this research rather than a product capability. The allowed states follow the owner’s later instructions instead of the older state names in `fields.md`.
