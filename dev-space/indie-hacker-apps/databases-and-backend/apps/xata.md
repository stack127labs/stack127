## Evidence rules

The task's six states override the different vocabulary in `fields.md`. `confirmed` means the scoped value is supported by the cited page. `not_published` is a bounded unsuccessful search, not proof of absence. `unclear` means available sources leave a material interpretation or entitlement open. `conflicting` preserves differing official descriptions. `check_failed` records failed access even where another official copy recovered the information.

Every row has an exact official URL, checked date and source-title/section note. Official HTML and Markdown copies, docs and the public API specification were compared. Versioned engine/extension-owner sources are used for upstream semantics only. No authenticated API endpoint was called and no tutorial command was executed. Vendor update dates are distinct from the checked date. All cost arithmetic is labelled **our calculation** and retains the published currency/units.

## Cost examples: our calculation

Checked date for all inputs and calculations: **2026-11-05**. Currency: **USD**, before tax. Region: **AWS us-east-1**, where the HTML page and official Markdown rate card agree on the base storage rate. These are planning calculations, not measured workload benchmarks or vendor quotes. Sources: https://xata.io/pricing ; https://xata.io/pricing.md ; https://xata.io/terms.

### Small SQL app, normal paid use

Approved scenario: one production database, 1 GB stored for the month, 100,000 reads, 20,000 writes, 10 peak connections, 5 GB internet transfer and 730 hours of availability. This example runs the primary directly on Xata; it does not add an external production database and a separately hosted production clone.

The micro reference rate is USD 0.012/hour. Its default max_connections is 50 and its default pool size is 45, so 10 connections fit those published defaults. Query counts do not establish sufficient CPU, memory or I/O. The HTML card calls the memory 1 GB, while the machine-readable rate card labels its memory column ram_gib; neither label is silently converted into the other. Production documentation requires at least 1 replica, so a single-instance starting price is insufficient for this production comparison. Sources: https://xata.io/pricing.md ; https://xata.io/pricing ; https://xata.io/docs/platform/branch.md ; https://xata.io/docs/core-concepts/deployment.md.

Let **B** be actual billed storage in the vendor's GB units, including any filesystem/other overhead that the usage meter counts. One GB of application payload does not prove B = 1. Production marketing describes primary/replica compute on shared NVMe-backed storage; it does not give a complete separate backup-storage tariff. Sources: https://xata.io/postgres-prod.md ; https://xata.io/docs/platform/branch.md ; https://xata.io/pricing.md.

| Item | Inputs and formula | Our calculated result |
| --- | --- | --- |
| Primary compute | USD 0.012/hour × 730 hours | USD 8.76 |
| One replica compute | USD 0.012/hour × 730 hours | USD 8.76, assuming a micro replica is permitted for this account/configuration |
| Compute subtotal | 2 × USD 8.76 | USD 17.52 |
| Storage | B GB × USD 0.28/GB/month | USD 0.28 × B; assuming exactly 1 billable GB gives USD 0.28 |
| Conditional compute/storage subtotal | USD 17.52 + USD 0.28 × B | USD 17.80 only when B = 1 |
| Internet transfer | 5 GB × applicable Xata transfer tariff, after allowance | Unknown: no matched public allowance/rate found |
| Full monthly total | Compute + metered storage + transfer + any required recovery/add-on charges + tax | **Incomplete** |

The monthly price card rounds micro compute to USD 9; our USD 8.76 comes from the hourly rate and the stated 730-hour scenario. It is not silently rounded to match the card. The resource-based tariff does not publish a read/write-count-to-compute conversion, and the source does not establish all backup/restore charges. Sources: https://xata.io/pricing.md ; https://xata.io/docs/platform/branch.md ; https://xata.io/postgres-prod.md ; https://xata.io/terms.

A **single-instance development comparison** would be USD 8.76 + USD 0.28 × B, or USD 9.04 if B = 1, before the same unknown extras. It is kept separate because the docs explicitly advise against zero replicas for production. Adding another replica adds its own active compute; workload performance and effective account limits still need assessment. Sources: https://xata.io/docs/core-concepts/deployment.md ; https://xata.io/postgres-prod.md ; https://xata.io/docs/api-reference/projects/get-project-resource-limits.md.

Trial-specific resource ceilings and its exact allocation were not published in the pages inspected, so a complete recurring month cannot be priced at USD 0. After the trial, use the paid tariff; Terms reserve trial deployment removal and potential deletion if no subscription is bought within 7 days after trial end. Sources: https://xata.io/pricing.md ; https://xata.io/pricing ; https://xata.io/docs/api-reference/projects/get-organization-resource-limits.md ; https://xata.io/terms.

For an **idle month**, keep the same stored data but enable hibernation and keep all branch instances asleep for the full 730 hours:
- Compute: 0 active hours × USD 0.012/hour × 2 instances = **USD 0**.
- Storage: B × USD 0.28 = **USD 0.28 × B**, not zero.
- If the month starts active and the documented default 30-minute inactivity delay applies, two micro instances add 2 × 0.5 hour × USD 0.012/hour = **USD 0.012** before hibernation. Open connections or scheduled work can alter inactivity, so this is an explicit assumption.
- Total remains incomplete because B and any retained-backup/other charges are not fully established.

### Copy-on-write test branch example

Assumptions: one micro child, active for 10 minutes and then deleted, with **0.1 GB of metered changed storage** for those 10 minutes. The 0.1 GB is an illustration, not a guaranteed fixed overhead. Parent/base storage and compute are already paid separately.

- Compute: USD 0.012/hour × (10/60) hour = **USD 0.002**.
- Changed storage: 0.1 GB × USD 0.28/GB/month × (10/43,800 minutes) = **approximately USD 0.000006392694** (rounded to 12 decimal places; invoice rounding is not established).
- Partial branch subtotal: **approximately USD 0.002006392694** (rounded to 12 decimal places), plus any network/recovery charges and the parent allocation.

This uses the specification's 730-hour (43,800-minute) month and its per-minute proration. It does not reuse the vendor calculator's default delta percentages as measured data. Parents and children share unchanged blocks, but after creation their writes do not synchronize and branches cannot merge. Sources: https://xata.io/pricing.md ; https://xata.io/docs/core-concepts/branching.md.

### Vector-search scenario

Assumptions: 100,000 vectors, 1,536 float32 values each, 1 KiB metadata each, 100,000 searches, 10,000 updates and 5 GB transfer/month. Xata's extension catalog lists pgvector 0.8.1; that upstream version stores a vector in 4 × dimensions + 8 bytes and allows 1,536-dimensional vector indexes. Sources: https://xata.io/docs/platform/extensions.md ; https://raw.githubusercontent.com/pgvector/pgvector/v0.8.1/README.md.

**Our calculation:** 100,000 × [(1,536 × 4) + 8 + 1,024] = **717,600,000 bytes** = **0.7176 decimal GB** using 1 GB = 1,000,000,000 bytes. Raw payload at the US storage rate gives 0.7176 × USD 0.28 = **USD 0.200928/month**.

This is a raw-vector/metadata illustration only. It excludes row headers, additional columns, index overhead, WAL, retained history, backups and working memory. Xata's actual billable GB interpretation/overhead must also be matched; the displayed rate does not prove a raw byte total is the metered size. CPU and index RAM cannot be determined from search counts. Embedding/reranking generation, transfer and production replicas remain separate. **Complete vector total: incomplete.** Sources: https://raw.githubusercontent.com/pgvector/pgvector/v0.8.1/README.md ; https://xata.io/pricing.md ; https://xata.io/docs/platform/branch.md ; https://xata.io/terms.

### SQL scheduling and full-backend scenarios

For the approved job scenario, pg_cron schedules **SQL inside the database**. It does not provide a separately shaped 0.5-vCPU/0.5-GB application worker. At 10,000 jobs × 1 active second, **our calculation** is 10,000 active job-seconds; the hypothetical per-job shape would represent 5,000 vCPU-seconds and 5,000 GB-seconds, but there is no matched container or per-second execution tariff.

Retry/wait illustration: if 1,000 jobs each run once more for 1 second, active time becomes **11,000 seconds**, with hypothetical resource equivalents 5,500 vCPU-seconds and 5,500 GB-seconds. If each original job waits 60 seconds, waiting totals **600,000 job-seconds**. These quantities cannot be converted into a Xata job invoice: database allocation is billed while active, missed-schedule/retry behavior is not a durable workflow contract, and an external app worker has its own provider rate. Peak 5 concurrent jobs is also a sizing requirement rather than a guaranteed pg_cron entitlement. **Both job totals: incomplete.** Sources: https://xata.io/docs/platform/extensions.md ; https://raw.githubusercontent.com/citusdata/pg_cron/v1.6.0/README.md ; https://xata.io/pricing.md ; https://xata.io/docs/platform/branch.md ; https://xata.io/docs/core-concepts/scale-to-zero.md ; https://xata.io/terms.

A full app backend adds 1,000 monthly active users, 1 GB files, 100,000 file reads, 10,000 uploads, 20 GB **total** internet transfer and 10,000 short function calls. For specificity, assume each external function actively runs for 1 second at 0.5 vCPU and 0.5 GB RAM; the current Xata offering does not identify that function machine, app-user authentication or file delivery as included. The 20 GB total replaces the database scenario's 5 GB rather than adding another 20 GB. Those external components, email/SMS where used and any AI-model charges need their own sourced tariffs. **Full-backend total: incomplete.** Sources: https://xata.io/docs/overview.md ; https://xata.io/pricing.md ; https://xata.io/docs/core-concepts/deployment.md ; https://xata.io/docs/platform/extensions.md.

The standalone 100 GB file-store scenario is **not applicable** to the current Postgres platform. Database data, backup objects and imported Parquet files are not an app bucket/storage-delivery product. Sources: https://xata.io/docs/overview.md ; https://xata.io/docs/core-concepts/deployment.md.
