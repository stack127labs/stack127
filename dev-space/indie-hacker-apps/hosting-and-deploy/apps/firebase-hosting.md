## Cost examples: our calculations

Calculated 2026-11-04; source inputs below checked that day. One builder, private source, registered custom domain, ordinary commercial use, no trial/credits/annual commitment/optional support. Domain registration and tax are excluded. Hosting's `$` prices are assumed USD for calculation; Cloud Run/SQL tables explicitly price USD. No silent currency conversion.

### A. Small commercial static site

Inputs: 100 MB output; 1,000,000 requests; 100 GB/month outbound; 20 builds × five minutes; one private repository/domain. Choose Blaze because traffic exceeds either published Spark allowance. Builds run on an existing local machine and upload with the CLI; no paid CI/build service is required by that workflow. This assumes no new builder-machine purchase or separately billed private-source service. Local time/electricity is not priced by Firebase and is excluded rather than declared free infrastructure.

Source inputs: https://firebase.google.com/pricing ; https://firebase.google.com/docs/hosting/usage-quotas-pricing ; https://firebase.google.com/docs/hosting/quickstart ; https://firebase.google.com/docs/hosting/github-integration ; https://firebase.google.com/docs/hosting/custom-domain .

Our calculation assumes no other site/channel usage and at most 20 retained complete 100 MB versions: `20 × 100 MB = 2,000 MB`. Even without storage deduplication this is below 10 GB. Therefore storage overage is $0 under this assumption. Build time is `20 × 5 = 100 minutes`; there is no Firebase-managed static builder charge in this chosen local workflow. Domain/certificate/CDN have no separate compulsory fee in the Hosting offer. The documented Hosting meters are storage and transfer, not request count.

The transfer rules conflict, so there are two calculations, not one exact advertised total:

- Quota guide's monthly allowance: `max(100 − 10, 0) GB × $0.15/GB = $13.50/month`.
- Pricing page's daily allowance: assume a 30-day month, uniform traffic, and decimal `360 MB = 0.36 GB`. `30 × max(100/30 − 0.36, 0) × $0.15 = $13.38/month`.

**Result: conditional static-hosting estimates of $13.50 or $13.38 before tax.** The second depends on daily traffic distribution, month length, and the stated decimal assumption. These are alternative interpretations of conflicting official sources, not a guaranteed invoice range. Actual billed transfer must also match the assumed 100 GB; compression/browser caching can change delivered bytes. No unconditional exact total until the allowance/reset conflict is resolved.

### B. Small commercial app API

Inputs: 1,000,000 requests, 100 ms active CPU work and 250 ms elapsed/request, 256 MiB working memory, 100 GB outbound, same builds/domain as A. Static Hosting alone cannot execute it. Select the documented Firebase Hosting + Cloud Run rewrite architecture, us-central1, request-based billing, 1 vCPU and 512 MiB memory, minimum instances zero, concurrency one. Allocated memory exceeds the working-memory input but actual app/runtime fit is untested. Publish the container with local Docker and Artifact Registry, not an assumed free Cloud Build workflow.

Source inputs: https://firebase.google.com/docs/hosting/cloud-run ; https://cloud.google.com/run/pricing ; https://docs.cloud.google.com/run/docs/configuring/billing-settings ; https://docs.cloud.google.com/run/docs/configuring/services/memory-limits ; https://docs.cloud.google.com/run/docs/configuring/concurrency ; https://docs.cloud.google.com/run/docs/container-contract ; https://cloud.google.com/artifact-registry/pricing .

Our calculation:

`active application CPU work = 1,000,000 × 0.100 = 100,000 seconds`

`request elapsed time = 1,000,000 × 0.250 = 250,000 seconds`

The first number is not the Cloud Run billed allocation. With concurrency one, the second is a useful unrounded processing input. For a specific illustration, assume requests create separate billed intervals, each rounded up from 250 to 300 ms, no free-tier usage elsewhere, and no startup/shutdown/extra minimum-instance time:

`billed processing time = 1,000,000 × 0.300 = 300,000 seconds`

`processing CPU = max(300,000 − 180,000, 0) × $0.000024 = $2.88`

`processing memory = 0.5 GiB × 300,000 = 150,000 GiB-seconds`, within the 360,000 free allocation; requests also fit the two-million allocation. These are conditional processing components. Contiguous/concurrent requests and actual startup time change the calculation.

Hosting delivery adds A's conflicting $13.38/$13.50 estimates if all 100 GB passes through Hosting. Artifact storage adds `billable excess GiB-hours × $0.000136986`; the workload specifies no image/layer size or retention, so this cannot be filled exactly. Backend networking and necessary runtime logs also need actual usage; read https://cloud.google.com/products/observability/pricing for logging allowances/rates. No compulsory separately purchased public IP or gateway is specified in the documented rewrite setup.

**Result: compatible in principle through an added backend; total unknown.** Known illustrative processing plus delivery is $16.26 or $16.38, before image storage, any backend networking, startup/shutdown allocation, applicable logs, and tax. These partial figures are not complete API prices. Hosting's 60-second limit fits the assumed 250 ms request but says nothing about real throughput.

### C. App plus persistent data

Inputs: B plus Postgres with at least 1 GiB RAM/10 GB storage, daily backups retained seven days, and 10 GB/month app/database traffic. Choose a separate Cloud SQL for PostgreSQL Enterprise shared-core db-g1-small in us-central1: 1.7 GiB RAM, single-zone, 10 GiB SSD storage, 730 running hours. This exceeds the storage requirement without silently equating GB and GiB. No trial, HA replica, or extended-support PostgreSQL version selected.

Source inputs: https://cloud.google.com/sql/pricing ; https://docs.cloud.google.com/sql/docs/postgres/instance-settings ; https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups . The instance-settings guide documents daily backups with seven-day retention; configure/verify that policy. Shared-core SQL instances have no Cloud SQL SLA. This database is neither included in Hosting nor a Hosting rollback target.

Our calculation, using published hourly rates:

`SQL instance = 730 × $0.035/hour = $25.55`

`SSD = 10 GiB × 730 hours × $0.000232877/GiB-hour = $1.70000210`

`known database compute + disk subtotal = $27.25000210` (about $27.25, explicitly rounded to cents).

`backup charge = used backup GiB-hours × $0.000109589/GiB-hour`.

A 10 GiB allocated disk does not fix the used backup size/change history, so no exact backup total is invented. Cloud SQL's published network table makes intra-continental transfer to other Google products free; app-side transfer and the selected connection route must also be checked. Cloud Run pricing notes additional charges for VPC connectors. Therefore 10 GB app/database traffic is not automatically a universal $0 end-to-end line item.

**Result: feasible through Cloud Run + Cloud SQL, with total unknown.** Formula: `B + $27.25000210 + used-backup charge + any required connection/network cost`. Database compute/disk is known; B is incomplete and backup bytes/connection setup are not fixed. The SQL Connect catalog's lower starting price/trial is not substituted for this resource requirement. A static or pinned-function rollback does not restore Postgres data.

- **New framework access:** https://firebase.google.com/docs/hosting/frameworks/frameworks-overview broadly describes preview Angular/Next.js support, while https://firebase.google.com/docs/hosting/frameworks/nextjs and https://firebase.google.com/docs/hosting/frameworks/angular explicitly close new participation in those experiments. - **Unpublished/unclear details:** searched Hosting quickstart, full configuration, custom domains, Hosting FAQ, quota guide, preview/recovery docs, framework guides, Firebase FAQ and governing terms before leaving values unresolved. - **Privacy/retention:** DPA, subprocessors, product privacy, and paid terms were read. They do not establish a Hosting-only regional guarantee for every file, request log, cache and backup. Approximate IP retention is kept separate from exported log retention and DPA deletion deadlines.
