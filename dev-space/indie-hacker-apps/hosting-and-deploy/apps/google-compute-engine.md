## Lifecycle and current status

Google Compute Engine is an active Google Cloud service offered to new customers. I found no notice that Compute Engine as a service is closing or being acquired. I checked the Compute Engine release notes and deprecation list, the Google Cloud Blog's Compute category, the Google Cloud product blog search, and the Google Cloud service terms. The release notes list current Compute Engine features through November 2026. The blog category page timed out when opened; searches of the official Google Cloud Blog for Compute Engine retirements did not return a relevant retirement notice. The deprecation documentation is the clearest source for current deadlines.

Retirement notices apply to specific features and hardware:

- NVIDIA P100 GPU support ended September 15, 2026. New or existing Compute Engine resources that use P100 GPUs can no longer be accessed.
- NVIDIA T4 and P4 GPUs were deprecated August 1, 2026 and are scheduled to reach end of support August 1, 2027. After that date, affected resources cannot be created, launched, or accessed.
- Customer-supplied encryption keys (CSEKs) were deprecated June 15, 2026 and are scheduled to be disabled June 16, 2027.
- The Compute Engine Usage Report, container startup agent, and serial console SSH key endpoint have also reached their listed shutdown dates. These are specific reports or features, not the VM service.
- The release notes also document active 2026 machine-series launches. None of these notices is an E2 shared-core retirement notice.

## Cost examples

All amounts are **our calculations**, not Google quotes. The VM, disk, and example egress rates are USD for Iowa (`us-central1`). The estimates use 730 hours in a month, one in-use external IPv4 address, and 100 GB decimal outbound to North America. The first 1 GiB of account-level free egress is assumed unused. For network conversion, 100 GB means 100,000,000,000 bytes, or exactly 93.1322574615478515625 GiB at 1,073,741,824 bytes per GiB. The calculated egress line is 92.1322574615478515625 GiB × USD $0.12/GiB = USD $11.0558708953857421875.

- `e2-micro`: compute 730 × $0.008376428 = $6.11479244; 20 GiB `pd-balanced` = 20 × 730 × $0.000136986 = $1.9999956; IPv4 = 730 × $0.005 = $3.65; egress = $11.0558708953857421875. **Known total: USD $22.8206589353857421875/month.**
- `e2-small`: compute 730 × $0.016752855 = $12.22958415; with the same 20 GiB disk, IPv4, and egress assumptions, **known total: USD $28.9354506453857421875/month.**
- `e2-medium`: compute 730 × $0.03350571 = $24.4591683; with the same 20 GiB disk, IPv4, and egress assumptions, **known total: USD $41.1650347953857421875/month.**

Scenario estimates using the field guide's workloads:

- **A, small commercial static site:** use `e2-micro`, 20 GiB `pd-balanced`, one IPv4, the stated 100 GB outbound, 20 five-minute builds, and a private source repository. Builds and Git access are customer-managed on the VM. The total is USD $22.8206589353857421875/month before tax and domain cost. No performance test was run.
- **B, small commercial API:** use `e2-medium` because it has a documented aggregate sustained CPU share of one physical CPU and 4 GiB RAM; include 20 GiB `pd-balanced`, one IPv4, 1 million requests, and the stated outbound. The total is USD $41.1650347953857421875/month before tax. Request capacity and app overhead are untested.
- **C, API plus Postgres:** self-host Postgres on the same `e2-medium`, use 30 GiB `pd-balanced` total, one IPv4, and the same outbound. The 10 GB/month app-to-database traffic is assumed to stay within the same VM and incurs no VPC transfer charge. The total is USD $42.1650325953857421875/month before tax, before snapshot storage and software-license charges. Database capacity and restore behavior are untested.

The calculations exclude optional support, DNS/domain registration, any premium image, separately billed Cloud Logging/Monitoring use, snapshots, taxes, and services such as a load balancer or Cloud NAT. A different billing account egress total, destination, region, or billing period changes the result. If the free first GiB was already consumed, add the applicable egress charge for that usage.

## Conflicts and unknowns

- The general-purpose VM pricing page's direct fetch timed out during this check. Google's official pricing search result displayed the E2 rates and Iowa region; the public network and disk pricing pages exposed their rates directly, so those pages are used for the examples.
- Google Cloud's blog Compute category page timed out when opened. Official blog searches for Compute Engine retirement/end-of-support notices did not return a relevant notice. The live Compute Engine release notes and feature-deprecation table were checked directly; no general service shutdown notice appeared there.
- The project-specific CPU and VM quotas are account/project values. Public docs explain how they work, but no Google Cloud project was accessed to read its live quota.
- Network connection timeout behavior varies by traffic path. One networking troubleshooting page names a 10-minute idle TCP timeout, but the reviewed docs do not establish that value for every path.
- Compute Engine product pages price E2 compute separately from persistent disks, networking, and OS licenses. This record does not include Cloud Run, App Engine, Cloud SQL, Cloud Storage, Cloud Build, Cloud DNS, load balancing, or NAT pricing as if they were part of the VM.

## Field problems

- Field 05 asks for the cheapest ongoing option. Compute Engine is a list of machine types and resources, not one plan; the examples use shared-core E2 sizes as practical small-VM references.
- Field 11's outbound price changes by destination and usage tier. The calculations assume North American destinations and the first 1 GiB account-level allowance remains available.
- Field 15's workload estimates are arithmetic only. They do not show that a shared-core VM can meet a real application's performance target.
- Fields 18–22 and 25–31 involve guest OS and app configuration. The VM service supplies infrastructure, not a managed framework, database, deployment, certificate, or application backup service.
- The terms distinguish customer data from service metadata. A VM region and regional disk selection do not prove that every billing, account, support, or control-plane record stays in that location.
