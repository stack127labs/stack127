## Cost examples — our calculation

Calculated 2026-11-05. One paying builder, lawful public commercial workload, one private source repository, one custom domain, **Paris PAR**, ordinary on-demand rates, no signup credit, no annual discount, no Premium option. All amounts are **EUR excluding tax**. Domain registration stays outside the hosting total. These are resource-usage estimates, not the initial cash top-up or exact invoice.

Clever Cloud meters application/dedicated-database running time by **second**. Its tariff expresses unit prices per hour. A thirty-day pricing reference is 720 hours; the required server comparison uses **730 hours**, not 720. The number of requests and active/elapsed request time do not replace the allocated-VM bill.

Common inputs:

- One private Git repository can deploy through local Git or authorised private GitHub integration, without a published mandatory extra Clever Cloud repository fee.
- One custom domain has free automatic Let's Encrypt after DNS setup. Generated `cleverapps.io` is explicitly for testing, so it is not used as the commercial domain.
- Twenty builds × five minutes = **100 minutes = 6,000 builder seconds = 5/3 builder hours**. We explicitly select a dedicated **S builder, 2 vCPU/2 GiB**, billed at **€0.044444444444444446/hour**.
- Builder line: **(100 ÷ 60) × €0.044444444444444446 = €0.074074074074074076…**, approximately €0.07. This is paid VM time, not a free minute allowance. Pico/nano always use a dedicated build/cache path; the selected builder is also explicit for XS in B.
- Standard load balancing, domain/TLS, basic logs/metrics/support do not require the separately quoted dedicated balancer/Unique IP/Premium products. The vendor's transfer statement excepts Cellar from its general absence of entry/exit fees, and the current public meter list has Cellar/Pulsar/storage traffic meters rather than an ordinary app-response tariff. Ordinary app transfer is therefore €0 under that published offer; unreasonable network use remains subject to AUP.
- No extra persistent app files, Cellar bucket, FS Bucket, preview app, worker app, task app, replica or external CDN is required by the three stated workloads.

## Field problems

- **05/07/15 — usage and cash funding differ.** Monthly invoices both settle use and fund the next period; compare resource consumption separately from the amount initially paid into the account.
- **06/07/37 — dynamic prices and legacy metadata.** Exact byte-valued capacities are useful, but the old catalog's zero/stale price fields cannot be used as the pricing authority. The current website's official component-to-tariff mapping was needed.
- **12/15 — deployment overlap.** Given build minutes do not specify VM startup or old/new replica overlap. Known per-second rates allow a transparent conditional formula; inventing a universal deployment duration would produce a false exact total.
- **15/24 — capacity is not throughput.** XS meets the stated one-vCPU/one-GiB allocation, but that does not verify the requested API's traffic performance. The smallest static plan also lacks a public uniform disk-size ceiling.
- **17/31 — data location is not one cell.** Compute may run internationally while default backups remain in PAR; account/support data have separate subprocessors and retention.
- **21/23 — jobs run with scaler lifecycle.** Cron runs per replica and stops/misses runs when instances stop; a Clever Task does not schedule itself. These conditions change costs and duplicate-run risk.
- **35/36 — hosted versus enterprise installable edition.** Managed-cloud self-host requirements are not applicable, but On-Premises exists and its conditional fields were investigated separately.
