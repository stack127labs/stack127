## Cost examples: our calculations

Calculated on 2026-11-04. These are formulas and partial estimates, not final comparable totals. One builder, commercial public product, one existing custom domain, monthly billing, no startup credits, no annual discount, no optional support. Region: US West Metal, California. Domain registration excluded. Tax amount/inclusion for self-service is unknown; all arithmetic below is before any added tax.

Inputs checked 2026-11-04:

- Container CPU `c = $0.00000772/vCPU-second`, RAM `m = $0.00000386/GB-second`, volume `v = $0.00000006/GB-second`, internet egress `e = $0.05/GB`: https://railway.com/pricing . Volume docs also publish `$0.000003472222222/GB-minute`; both versions are retained because they differ: https://docs.railway.com/pricing/plans .
- Monthly bill relationship `max(plan minimum, resource usage)` and minimums Hobby `$5`, Pro `$20`: https://docs.railway.com/pricing/understanding-your-bill . This is a steady-state monthly attribution, not the invoice's mix of prepaid subscription and previous-cycle overage.
- Service builds and associated images free: https://docs.railway.com/pricing/plans . Free certificates: https://docs.railway.com/networking/public-networking . Private DB communication avoids egress: https://docs.railway.com/pricing/cost-control .
- Services can be built from local source or GitHub: https://docs.railway.com/services . Exact private Git repository eligibility remains unverified. A private container registry instead requires Pro: https://docs.railway.com/builds/private-registries .
- Running idle still uses billed resources: https://docs.railway.com/pricing/understanding-your-bill . Database and volume restrictions: https://docs.railway.com/databases/postgresql and https://docs.railway.com/volumes/reference . Backup schedule/pricing: https://docs.railway.com/volumes/backups .

No request meter is shown in checked pricing; that absence is not treated as an explicit inclusion guarantee. Likewise a missing gateway/IP/log line item is not invented as an additional fee or silently certified as free. These evidence gaps prevent a fully verified total.

### A. Small commercial static site

Inputs: 100 MB deployed files, 1,000,000 requests, 100 GB outbound/month, 20 five-minute builds, one private source repository and custom domain. Compatible in principle through a static-file serving container; CPU/RAM consumption of that server is unspecified. Select Hobby for the cheapest paid illustration; Pro is the vendor's commercial recommendation.

- Transfer: `100 GB × $0.05/GB = $5`.
- Build input: `20 × 5 = 100 minutes`; service build cost `$0` under documented free-build policy.
- Files: source/image storage included in free build/image policy; no persistent volume needed for immutable deployed files.
- Formula: `U_A = $5 + c × CPU_A_seconds + m × RAM_A_GB_seconds`; `bill_A = max($5, U_A)` on Hobby, or `max($20, U_A)` on Pro.
- Result: exact monthly total unknown. `$5` is the priced transfer component, not the full hosting quote. Private repo and billing-inclusion gaps above remain.

### B. Small commercial app API

Inputs: 1,000,000 requests; 100 ms active CPU and 250 ms elapsed/request; 256 MiB working memory; 100 GB outbound; same builds/domain/private repo as A. Always-on service for 730 hours with ceiling/capacity of at least 1 vCPU and 1 GiB memory is required by the field specification. Hobby capacity exceeds these ceilings, but Railway meters usage rather than selling a fixed 1-vCPU/1-GiB server allocation. Actual capacity/throughput is untested.

- Running period: `730 × 3,600 = 2,628,000 seconds`.
- Request work: `1,000,000 × 0.100 = 100,000 CPU-seconds`; at the container rate this component is `$0.772`. No inference about actual vCPU speed is made.
- `1,000,000 × 0.250 = 250,000 request-elapsed seconds` does not equal the app's running time; overlapping requests and idle memory exist.
- Let `M_B` be measured RAM in vendor GB-seconds and `H_B` the additional idle/framework/startup CPU-seconds. `U_B = $5 + $0.772 + c × H_B + m × M_B`.
- If, strictly as an added assumption, the process continuously consumes exactly one **vendor GB** over 730 hours, memory component is `2,628,000 × $0.00000386 = $10.14408`. This is not a claim that one vendor GB equals 1 GiB or that the requested 256 MiB app consumes exactly this amount.
- A full busy vCPU for 730 hours would cost `2,628,000 × $0.00000772 = $20.28816` for CPU alone. It is not the expected CPU usage and is not added to the request-work component.
- Result: `bill_B = max($5, U_B)` Hobby or `max($20, U_B)` Pro; exact total unknown. Idle/runtime overhead, GB/GiB metering and the inclusion/private-repo gaps remain. Do not label `$5.772` or either component example as the full workload cost.

### C. App plus persistent data

Inputs: B plus one Postgres with at least 1 GiB memory, 10 GB storage, daily backups retained seven days, 10 GB/month app-to-DB traffic. Select Pro because the published Hobby volume ceiling is 5 GB. A single node is not an HA database.

- DB memory and CPU billed by consumption: add `m × M_DB + c × CPU_DB_seconds`; no reserved-memory database plan price documented.
