### B. Small commercial app API

Inputs: stateless HTTP app, one million requests/month, assumed 100 ms active processor work and 250 ms total/request, 256 MiB working memory, 100 GB outgoing; same builds/repository/domain as A. Required server allocation at least one vCPU and 1 GiB RAM for 730 hours.

The selected **2-vCPU/4-GB** target satisfies this allocation floor. Four decimal GB exceeds 1 GiB, but the memory is for the whole VM, including OS, proxy, monitoring, build processes and the application. It is not four GB reserved independently for every container. CI-CD-Target's documented minimum is 1 vCPU/2 GB; a cheaper one-GB packaged-service starting price is not substituted. [Resources/rate](https://elest.io/pricing); [Target minimum](https://elest.io/open-source/ci-cd-target/resources/quickstart).

**Our calculation: 730 × $0.022 + $0 extra request/build charge + $0 transfer overage under A's assumptions = $16.06 before tax.** This is the same server bill because there is no function-invocation price. Workload arithmetic is 1,000,000 × 0.1 = 100,000 active processor-seconds and 1,000,000 × 0.25 = 250,000 elapsed request-seconds. Neither is substituted for the 730 hours of booked capacity. The pricing/configuration does not prove the workload meets its latency target.

The default limiter is **150 web requests/minute/IP** and GET responses are cached for **three seconds**. Both can be configured. For comparison, one million evenly spaced requests over 730 hours averages approximately **22.83105 requests/minute**, our rounded calculation; bursts or concentrated client IPs can still hit the default. Review API cache correctness and rate settings before a load test. A protocol-specific WebSocket/streaming guarantee was not established.
