## Cost examples — our calculation, estimated

### What gets counted

Fixed uptime inputs: **5 / 25 / 100 HTTP endpoints**, every **60 seconds**, **one active checking path per endpoint**, **30 days**, email alerts and **one own-domain status page**.

Minutes in month = 30 × 24 × 60 = **43,200**. The template runs **one main scheduled Worker invocation each minute** and loops through all monitor entries.

| 100 | 4,320,000 | 12,960,000 | 43,200 | 300 |

Formula: target checks = endpoints × 43,200 × paths. Target fetches are **subrequests**, not automatically the same number of chargeable main Worker invocations. Additional worker-to-worker/DO/proxy activity, redirects, fallback checks, page/API visitors and other account projects have their own effects.

The README advertises **up to 50 checks**. **100 entries**, or **75/300** entries for the larger three-path scenarios, exceed that published scope. Source iterates the monitor array, but a larger array is not proof the Free plan or a Paid deployment can execute it reliably. Free CPU is **10 ms per invocation**, Free subrequests **50/invocation**; the app also makes a location trace request and can send webhooks. No maximum safe monitor count was benchmarked here.

The default scheduler location is chosen by Cloudflare and can vary. A **worker://region** hint is best effort; it is not a guaranteed exact geographic origin. Self-hosted proxy paths can select an operator-controlled network, but require extra infrastructure/cost and were not tested.

### Storage operations and conditional base cost

The main Worker reads **one compacted state value from D1** each scheduled run, then upserts that value on a status change or after the default **3-minute write cooldown**. It does not insert one D1 row for every target check.

Under an explicitly idealized steady-state assumption — exactly one cron tick per minute, no status/error changes, default cooldown, no page/API visitors, no setup/migration queries — planned SQL operations are:

- Main state reads = **43,200/month**, or **1,440/day**.
- State upserts = 43,200 ÷ 3 = **14,400/month**, or **480/day**.
- If state changes on every tick, state upserts can reach **43,200/month**, or **1,440/day**, before exceptions/additional calls.

These count application SQL calls, not a guarantee of exact billable D1 rows. Scanned/indexed rows, page/API queries, other account usage and migrations still matter. State size must fit the **2,000,000-byte D1 row/string limit** as well as the plan's database limit. That single-row restriction does not disappear by upgrading to Paid.

| 5 endpoints | 0 | $0 if all account/runtime limits are met | $5 USD/account/month before overages | Unknown |

The known default main-call counts are well below the **100,000/day Workers request**, **5 million/day D1 row-read** and **100,000/day D1 row-write** allowances under the narrow assumptions. That does **not** establish adequate CPU, subrequests, state-row size or a complete working free deployment. Published allowances are shared account limits, not new independent quotas for every app.

For Paid, let **R** be all billable Worker/Pages requests, **C** total CPU milliseconds, **Qr/Qw** D1 billable rows read/written, and **G** stored D1 GB-month. The main Workers/D1 part is:

**$5 + $0.30 × max(0, R − 10,000,000)/1,000,000 + $0.02 × max(0, C − 30,000,000)/1,000,000 + $0.001 × max(0, Qr − 25,000,000,000)/1,000,000 + $1 × max(0, Qw − 50,000,000)/1,000,000 + $0.75 × max(0, G − 5)**.

Add any **Durable Object request/duration/storage charges**, logs, external proxy/Globalping/Apprise/email charges, domain registration, deployment-account overage and applicable tax. Provider-specific billing rounding still applies. No CPU or DO-duration input was measured, so neither **$0** nor **$5** is presented as a complete exact bill.

The email requirement needs an external compatible webhook/Apprise service; no included email sender or allowance is established. Own-domain setup is documented, but registration is separate. No full three-path total is calculable without deciding the proxy mode and measuring the added meters.

### Three-path geo checks

One entry has **one** checkProxy. Repeating each endpoint under **three distinct monitor IDs** can create three check paths, but no native quorum/combined per-endpoint incident is established. Do not call a hint a guaranteed city or treat local fallback as the intended remote origin.

For **worker://** paths, the checked code calls **getLocationAndStatus** and **kill** on the RemoteChecker. Each RPC method call is a separate DO request under Cloudflare pricing. Assuming both calls happen once and no errors/retries/other usage:

- DO RPC sessions = target checks × 2.
- Three-path small case: 648,000 × 2 = **1,296,000/month**, or **43,200/day**.
- Growing: 3,240,000 × 2 = **6,480,000/month**, or **216,000/day**.
- Busy: 12,960,000 × 2 = **25,920,000/month**, or **864,000/day**.

Free DO requests include **100,000/day**; the latter two illustrative request counts alone exceed that quota, as well as the project's 50-entry scope. Paid includes **1 million/month**, then **$0.15/million**, plus duration above **400,000 GB-s/month** at **$12.50/million GB-s**, with provider billing-unit rounding. Duration is wall time at the provider's allocated memory, not Worker CPU time; it is unmeasured here. Other proxy choices have different costs. These arithmetic examples do not prove the larger configuration can run.
