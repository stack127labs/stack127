Warnly is a free MIT-licensed exception-monitoring server for your own infrastructure. It receives Sentry-style error envelopes, groups them into issues and supports team assignment and threshold webhooks. Current explicit platform identifiers are Go and Rust. The site's broader SDK, instant-alert and single-command claims need qualification from current source and setup docs.

The current code uses 90-day event retention and a 1 MiB envelope-body limit. Its default analytics backend uses ClickHouse alongside metadata MySQL; newer source also offers a MySQL/DuckDB-engine backend. Public setup docs are older than several implementation changes, including a required notification-encryption key and a newer build-toolchain version. No installation or runtime behavior was tested.

## Cost examples: our calculation, estimated

Warnly has no paid software plan, currency-based subscription or per-report vendor rate. **Software license cost = 0** under the MIT grant. That zero is not an all-in monitoring bill and is not a quoted USD/EUR price. Hosting providers choose their own currencies and conditions; no exchange rate or silently invented hosting price is used here.

Only the error family applies. The homepage's “Performance First” describes Warnly's own intended processing speed, not customer application tracing. No separate log-GB, request-based APM or external uptime/job-ping total is calculated without a documented product path.

### Error workloads

Inputs held constant: one builder, three supported backend app projects, 5000 / 50000 / 500000 captured error reports/month, at least 30 days of detail, no paid replay or AI extra. Assume each report fits the 1048576-byte envelope limit and follows the implemented Sentry error-event path. Grouped issue count does not replace report count.

The publisher advertises unlimited projects/users/events without commercial tiers. Current source assigns **90-day** event retention; this meets the minimum 30-day detail requirement, but requires retaining more history than a 30-day storage budget. No supported exposed retention setting reducing the current 90-day assignment to 30 was recovered.

| Workload | Software-fee formula | Our estimated software result | Complete recurring result |
| --- | --- | --- | --- |
| Small: 5000 reports/month | Free MIT license; no per-report price or paid three-project upgrade | 0 license/subscription fee | Unknown infrastructure/operations cost |
| Growing: 50000 reports/month | Same free license; no commercial event overage | 0 license/subscription fee | Unknown infrastructure/operations cost |
| Busy: 500000 reports/month | Same free license; no commercial event overage | 0 license/subscription fee | Unknown infrastructure/operations cost |

Our full-cost formula is:

**Recurring cost = Warnly license (0) + Warnly server compute + metadata database + analytics database + storage + backups + traffic + optional identity/webhook services.**

Costs may share one rented host, but must not be counted twice if a selected host already bundles those resources. A custom deployment could add queue infrastructure. Labor and support operations are excluded from the cash formula rather than represented as free. Taxes, domains/certificates and any external messaging tariff depend on the chosen infrastructure and are not priced here.

A complete total cannot be exact because the publisher supplies no workload-specific CPU/RAM/disk recommendation, event-size distribution, storage compression/index overhead, backup policy or production availability target for these workloads. The README's demo uses **1 vCPU/4 GB** on contributed infrastructure. It does not identify monthly report volume, burst rate, disk capacity, query load, databases colocated, or retained-byte footprint sufficient to size these scenarios. It must not be treated as donated production hosting available to the reader.

### Retention/storage inputs: our calculation, estimated

This is a workload model, not a measured disk requirement. Assume a steady uniform rate, 30-day calculation months and no lost/rejected reports. For **R monthly reports** and **90-day retention**, a simple retained-count model is:

**Retained events ≈ R × 90 ÷ 30 = 3R.**

| Monthly reports | Modeled 90-day event count | Byte formula before database/index/backup overhead |
| --- | ---: | --- |
| 5000 | 15000 | 15000 × unknown stored bytes/event |
| 50000 | 150000 | 150000 × unknown stored bytes/event |
| 500000 | 1500000 | 1500000 × unknown stored bytes/event |

The 1 MiB envelope cap is an **ingestion maximum**, not the average stored record size. It cannot be multiplied into a “typical” disk estimate. Grouping does not eliminate individual retained occurrences. Metadata/issues/comments, primary indexes, replicas, backups, optional queue retention and TTL purge delays require additional capacity.

No host rate was selected because there is no source-backed production sizing that would justify choosing a particular VM for the common workloads. H02 remains unknown rather than pricing an arbitrary server as though it met the task.

Current README says backend exception monitoring remains in progress, frontend/mobile and broader alerting are unfinished, and future maintenance carries no promises. Latest release metadata still lists v0.7.2 on 2026-10-14 and the repository is not archived. Use an available-but-qualified lifecycle description, not shutdown or guaranteed active support. - **SDK breadth:** homepage says rich SDKs for all major languages. Quickstart establishes Sentry-envelope compatibility, while current platform/SDK identifiers explicitly name Go/Rust. Deserializer code handles additional exception JSON shapes, which is not a supported-version test matrix for every Sentry SDK, browser, mobile runtime, attachment and compressed envelope.
