# stack127 tool content integration

Use this skill after `$stack127-tool-writing` in the normal pipeline, or when a user supplies replacement copy. Read the draft files or supplied words, the spec, `stack127_docs/page-publishing.md`, `stack127_docs/tool-pages.md`, `stack127_docs/tool-catalogs.md`, `stack127_docs/seo.md`, `stack127_docs/shared-ui.md`, the route, and current development rows. Map the copy into the visible title, introduction, usage, supporting content, search title and description, and shared catalog card copy. Interface words live in frontend code, which the Opus writing session updates; do not edit UI code. Use `stack127_docs/writing-style.md` for any wording edits. If a required field is missing or a claim conflicts with the tool or sources, return it to the main agent for the writing session or resolve it with the user; do not invent replacement copy.

1. Write the tool's publish manifest in `tmp/page-publishing/<slug>/`, with the Markdown files beside it. Put the title, introduction, usage Markdown, supporting Markdown, and supported content components or figures in their intended fields, using the documented Markdown syntax. Add `meta_title` and `meta_description` to the registry patch when the draft changes them. An unpublished page returns 404, and the publisher's check expects that 404. For a new tool in the pipeline, set `registry.is_published` to `true` explicitly so the development page can be previewed. Its catalogs must be published too. The same value carries to production at release. For other edits, leave publication fields alone unless the main agent asks.
2. Read the spec's Catalog placement and the current catalog memberships. Confirm that the primary and every secondary catalog exist. Choose an unused display order for each new placement and the approved card icon and registered tool-specific art key. A new tool cannot use the `icon` art fallback. Put the card fields and the complete ordered catalog list in the manifest. Do not put cards in route code. If a new catalog is required and the main agent has not supplied it, return that work before using a substitute placement.
3. Add the readiness requirements: the route file, the registered art file, any read-only SQL checks the tool needs, and smoke paths with expected visible text.
4. Start `npm run dev` and `npm run stack127:cache:watch:local` as background services. Run the tools publisher's `prepare` and `preview` against development and review the result, then run `apply`. It also checks the public page. If it says the batch committed but the check failed, run `verify` with the same plan. Catalog card edits and membership changes do not change `tool_version`. Set a new version only when the main agent names one.
5. Run only focused renderer, link, figure, or data checks when the changed code needs them.
6. Open the actual development tool page and every assigned catalog, using the headless fallback in `skills/stack127/references/homelab-browser-and-search.md` when needed. Confirm the integrated content, card words, links, search metadata, and primary tool action work. For a published new tool, inspect its drawing at the real card size at desktop and mobile width in dark and light themes; simplify the spec and regenerate if its subject, spacing, or contrast fails. Unpublished tools stay out of public catalog cards until their registry row is published; inspect the generated art at card size and flag the public-card check for publication.

When copy fixes come back, update the manifest's files and run the publisher in development again, so the manifest always matches what was checked. The single-purpose tool-page commands are fine for a quick development check.

If the main agent wants a public page kept out of search while it is still being improved, set `registry.is_indexable` to `false`. New pages default to `true`; existing pages keep the setting when omitted. A published noindex page still appears in catalogs and sidebars. Check its own canonical, noindex robots tag, no JSON-LD, and absence from the sitemap.

Do not calculate hashes, write receipts, or run a browser matrix. This integration task permits guarded development updates. Production data, commits, pushes, and deployment need a separate coordinator-approved task under the rules in `AGENTS.md` and the release skill. Report the manifest path, changed fields, catalog ranks and orders, version, focused checks, and remaining issues.

For an existing tool, a change to inputs, results, calculations, validation, or other user-visible behavior needs a `tool_version` increase. Use a patch for a compatible fix, a minor version for compatible new behavior, and a major version for an incompatible contract change. Confirm the version with the coordinator before integration. The database moves the public date when the version changes. Copy-only edits move the date without changing the version. Card-only edits refresh catalogs and keep the tool date unchanged. See `stack127_docs/tool-pages.md`.
