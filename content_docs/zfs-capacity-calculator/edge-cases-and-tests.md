Status: ready
Tool: ZFS Pool Capacity Calculator
Route: `/zfs-capacity-calculator`
Depends on: `competitive-report.md`, `implementation-report.md`, `brief.md`

## Risk model

| Priority | Meaning for this tool |
| --- | --- |
| P0 | The tool shows materially wrong capacity, loses a vdev boundary, counts an auxiliary role as general data, keeps a plausible stale result, emits an unsafe command, accepts hostile shared state, leaks private topology, or makes calculation inaccessible. |
| P1 | A common construction, validation, recovery, share, reload, keyboard, focus, responsive, or theme flow fails without changing the core formula. |
| P2 | An uncommon presentation, long-value, copy fallback, reduced-motion, or layout-resilience issue makes the result harder to inspect but leaves the answer and recovery intact. |

Every P0 and P1 case below has an automated owner. Manual review supplements hierarchy and visual judgment but is never the only proof for a P0 or P1 requirement.

## Test data and mocks

- Keep all page-owned formula fixtures under the ZFS calculator test directory. Use small binary capacities such as 1 MiB for hand-verifiable arithmetic and realistic decimal 18 TB inputs for formatting and interaction.
- Define deterministic constructors for mirrors and RAIDZ1/2/3, mixed members, every auxiliary role, just-inside/outside counts, and the maximum 256-drive UI topology. Generated matrices use fixed loops, never randomness.
- Use exact constants for `KiB`, `MiB`, `GiB`, `TiB`, decimal TB, the 128 MiB slop floor, and 128 GiB cap. Expected results are literal `bigint` values from FF-001 to FF-016, not calls to production helper equations.
- Shared-state fixtures must be created by the real version 1 encoder for valid cases. Malformed fixtures mutate one envelope property at a time: encoding, JSON, UTF-8, schema, engine, calculator, input version, payload type, prototype key, reserved tag, size, depth, and topology.
- Clipboard tests mock only `navigator.clipboard.writeText`, once resolving and once rejecting. Network tests abort unexpected fetch, XHR, WebSocket, and worker creation. Analytics tests spy on the existing site hook if present and assert absence of value-bearing properties.
- Long-string fixtures use inert plain text and HTML/shell/URL-shaped payloads without execution. Command tests assert token arrays and rendered plain text, never run a shell.
- OpenZFS fixtures use explicitly named disposable sparse files and pools inside a validated temporary directory. The future script must refuse real block devices, require the expected OpenZFS version, print cleanup commands before creation, use `zpool create -f` only inside its own disposable fixture boundary if unavoidable, and destroy only its exact generated pool name. The page command preview remains `-n` and never includes `-f`.
- For OpenZFS allocation receipts, disable compression and dedup, set copies to one, write deterministic incompressible full-size blocks, sync, and record `zpool status`, `zpool get -Hp`, `zfs list -p`, and `zdb` block details. Use per-data-block LSIZE/ASIZE as the exact oracle. Pool-level free/available values are evidence only because labels, metaslabs, metadata, and allocation history are outside version 1.
- Store fixture receipts with OpenZFS version, operating system, command, topology, sparse-file bytes, `ashift`, block size, write size, expected values, observed values, tolerance kind, and date. Fresh-pool per-block tolerance is exact equality. Expansion is an expected non-equivalence, not a numeric capacity oracle.
