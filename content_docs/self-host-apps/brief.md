# Brief: Self-host apps

## Who is here

A self-hoster knows roughly what they want to run and is comparing apps against their server, storage, deployment method, source model, price, and maintenance expectations. They want open and closed-source choices in one place, with verified facts faster than another recommendation article.

## The job

They should narrow the directory, compare credible candidates, open a complete record, and reach the app's official site, source when available, container registry, or platform catalog without guessing which facts were verified.

## Search intent

The primary query is `self hosted apps`. Supporting queries are `self hosted apps directory`, `open source alternatives`, `Docker apps`, `self hosted software`, and category-specific alternative searches. The page should answer discovery and comparison through useful fields. It should not repeat keyword variants in introductory copy.

## Data-quality contract

Every actionable unknown enters a research queue. Official project sites, source repositories, license files, release feeds, container registries, and install documentation are preferred in that order for their relevant facts. A researched null is valid when the project does not publish a minimum, price, database requirement, container image, or storage estimate. Reviewed planning ranges may fill a comparison gap only when they carry an evidence URL, basis, confidence, and an explicit `estimated` label. The UI must distinguish a researched null from a field that has not been researched. Published records may include open-source, source-available, and closed-source apps when self-hosting is verified. Missing license and source-model facts block records that claim source availability. README fallbacks remain visible as weaker documentation evidence until a dedicated official page is found.

## Show vs say

Official app images are normalized into the public stack127 Supabase bucket. Preserve these managed URLs when importing or updating records.

Use the approved Fact rows design from the card lab. Three cards fit beside the desktop sidebar, with two and one columns at narrower widths. Each card shows the actual app image, name, primary category and a +N count, full summary, then labeled rows for Source, Pricing, RAM, Storage, and Last update. Each row has a small semantic icon. Keep estimates and unknowns explicit. Clicking anywhere on the card opens the existing details drawer; do not link the whole card to an external site or redesign the drawer in this pass.

Filters and the card grid do the discovery work. The dotted header uses one small server-rack drawing to identify the collection. Category, source model, install method, and license use compact controls. The detail drawer separates identity, installation destinations, system requirements, data services, release activity, source links, and uncertainty. App logos prove identity, while one-sentence summaries explain purpose. The page uses a generated monogram only when the app image is missing or fails to load. Counts are live database facts. Longer prose is reserved for uncertainty and the limits of a field.
