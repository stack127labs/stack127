# Visual first: how stack127 pages show instead of tell

People do not read this site line by line. They scan, find the thing, and leave with it. So every page is planned as a set of visuals connected by a few good sentences, not as an article with pictures added later.

This doc covers the media system, when to use which, the page brief, and the rule that you push back on text-heavy requests.

## The push-back rule

When someone asks for a page ("let's write a page about software licenses"), the first deliverable is a format proposal, not a draft. Look at the subject, decide what each part should be (chart, table, drawing, screenshot, sentences), and answer with the mix:

"Most of this page wants to be a verdict table per license and one marker drawing of how copyleft spreads. The writing is maybe six sentences: what a license is, and one recommendation. Here is the plan."

This applies to everyone, including Teja. If the request is text-first and the subject is not, say so and suggest the better format. Text wins only when the content is genuinely a story, a judgment, or a caveat.

## The four media, and when each one wins

**Marker art** explains concepts, vaguely on purpose. Hand-drawn, one idea per figure, semantic tones, never used for exact numbers. "How copyleft spreads", "where your data lives", "what a reverse proxy does". If a reader could argue with the pixel positions, marker art was the wrong choice. Pipeline: `stack127_docs/marker-art.md`, generated by `npm run stack127:marker-art`.

**Clean charts** state data, precisely. Straight lines, real axes, exact values, tabular numerals. Prices, benchmarks, RAM usage, counts over time. Anything a reader might quote or compare goes here, never in marker style and never in a paragraph. Pipeline: same spec-driven system at `scripts/stack127/clean-charts/`, generated by `npm run stack127:clean-charts`, rendered with the `Chart` component (`app/chart.tsx`).

**Tables** compare repeated facts across items. If three or more things share the same fields, that is a table. Sentences describing "X has A, while Y has B, and Z has both" are a table wearing a costume.

**Screenshots** prove reality. A real interface, a real result, a real setting. Dark theme, default viewport 1280 wide unless the subject is mobile, cropped to the subject, no arrows or circles drawn on top unless one specific control is the whole point. Run them through the cover-image-intake skill treatment: junk metadata stripped, clean SEO metadata kept. Screenshots go through `MediaFigure` with the `image` kind; captions are one sentence saying what the reader is looking at.

Everything visual carries its takeaway as the caption. If you cannot caption it in one sentence, it is two visuals.

## What sentences are for

Sentences carry judgment, story, and caveats: the recommendation, the gotcha, the "why this matters", the one confusing thing explained where the confusion happens. That is real writing and it stays first person and casual, per `writing-style.md`. What sentences never do here: recite numbers, walk through comparisons, or describe what a visual already shows.

## Every page has a brief

`content_docs/<page-slug>/brief.md`, half a page, written before the page. Three sections:

```markdown
# Brief: <page name>

## Who is here
One or two sentences. The actual person, what they were doing when they
landed, what they already know.

## The job
What they leave with: an answer, a running thing, a decision.

## Show vs say
The format mix. Which parts are a chart, table, drawing, or screenshot,
and the few things that genuinely need sentences.
```

The brief is the contract: if the brief says "verdict table", the page does not grow four paragraphs of license prose later. Update the brief when the page's job changes. New pages need the brief before implementation; existing pages get one when they are next reworked.

## A worked example

The request "write a page about software licenses" becomes, after the push-back:

- a verdict table per license (the eight facts already in the data)
- one marker drawing: how copyleft obligations spread from code to service
- one clean chart only if there is real data worth charting (there is not, so no chart)
- sentences: what a license is in two lines, one recommendation per audience, and each license's one common mistake

That is the whole page. Everything else the old version said in paragraphs was a table row wearing a costume.

## Planning order for any page

1. Read or write the brief.
2. List the claims the page makes.
3. Assign each claim a medium using the table above. Default is not-prose.
4. Make the visuals (specs for figures and charts, capture screenshots).
5. Write the connecting sentences last, in the `writing-style.md` voice.
6. Run the quick check in `writing-style.md`.
